# Campus Atlas V1.7 — API-first simplification spike

**Status:** Documentation-only architecture spike

**Authority:** Governed by the frozen [V1.7 implementation blueprint](V1.7_IMPLEMENTATION_BLUEPRINT.md)

**Baseline:** `main` at `75119ff67007ddbe002b856573bc74126643e180`

**Production behavior changed:** No

This spike defines a simpler operational API over the canonical V1.7 engine.
It does not change production behavior, persistence schemas, roadways, ranking,
packet compilation, handoff behavior, or any dogfood record.

The existing application remains the advanced stewardship, governance, and
inspection console. The proposed API becomes the narrow operational path for
an API sidecar, integration, pilot, or future thin client.

---

## 1. Decision record

Campus Atlas has proved the local causal loop through immutable packet
compilation. The next problem is not a missing ontology or another reasoning
feature. It is that the current product exposes too much of the internal
pipeline as the default workflow.

The approved direction is:

1. Preserve the compiled packet and existing dogfood records.
2. Do not dispatch a paid receiving-model handoff yet.
3. Add a thin `continuity/check` and `reconstruction/run` façade over the
   existing canonical services.
4. Keep Inspect as the advanced audit console rather than the main operational
   workflow.
5. Evaluate the engine with deterministic receivers and replay fixtures that
   incur no model-provider cost.
6. Keep eventual handoff provider-agnostic and friendly to bring-your-own-key
   deployments.
7. Perform one real paid provider call later when funding, credits, a
   collaborator, or a pilot makes that appropriate.

This is an interface and product-boundary simplification. It is not a rewrite
of the canonical engine.

## 3. Product boundary after the simplification

Campus Atlas remains a governed reasoning-context continuity steward.

- Cody or the caller supplies the current task.
- Atlas checks whether governed continuity is applicable.
- Atlas reconstructs an immutable, bounded context packet when asked.
- A receiving model, selected separately, reasons and answers.
- Atlas records what it supplied and why.
- Inspect exposes the full lineage and governance history.

The operational default should answer two questions:

1. **Does Atlas have legitimate context for this task?**
2. **What exact governed reconstruction should a receiving model receive?**

The default path should not require a caller to understand checkpoints,
reasoning nodes, finding versions, governance-event internals, packet-item
ancestry, or handoff lifecycle tables. Those records remain essential and
inspectable, but they are audit structures rather than the basic integration
surface.

## 5. Proposed operational architecture

```text
Caller task
   |
   v
continuity/check  -- no canonical mutation, no provider call
   |  interpret roadway, enforce project/case scope, preview treatment
   |  return compact eligibility + ambiguity + missing-state result
   v
reconstruction/run -- idempotent canonical write
   |  rerun against current canonical state
   |  compile packet + receipt atomically through existing services
   v
Immutable packet and causal receipt
   |
   +--> caller uses packet directly
   +--> optional later provider-neutral handoff (separate consent/cost boundary)
   +--> Inspect exposes complete lineage and audit history
```

The façade is additive. Existing project-scoped routes remain the advanced and
compatibility surface until implementation and parity tests establish that a
consumer can use the façade safely.

## 5A. Runtime state versus durable knowledge

The operational API needs an explicit boundary between the state of one
client run and the canonical knowledge that may affect later reasoning.

### Runtime state

Runtime state exists to coordinate one request, review, or dispatch. Examples
include:

- Current client run ID
- Temporary roadway override
- Selected token budget
- Current review policy
- Transient ambiguity resolution
- Progress state
- Provider dispatch consent
- Current UI stage

Runtime state may be mutable during the run and may be logged as bounded
telemetry. It must not automatically become a finding, mechanism, correction,
principle, project preference, retrieval authority, or durable source claim.
Selecting a roadway for one run does not update the roadway registry. Accepting
a packet for one answer does not approve its contents as a future mechanism.

### Durable canonical knowledge

Durable knowledge is created only through the existing canonical source,
reasoning, governance, packet, and receipt services. Examples include:

- Exact messages and events
- Reasoning-node versions
- Findings and finding versions
- Governance events
- Mechanisms and mechanism versions
- Outcomes and postmortems
- Immutable packets and packet items
- Immutable receipts

The current implementation already enforces much of this split:

- Conversation messages and Exact source events are immutable source records.
- Checkpoints and reasoning-node versions preserve analysis history without
  creating authority.
- Findings remain proposed until a governance event changes eligibility.
- Mechanism versions preserve Cody's governed wording and scope.
- Temporary roadway overrides live in one interpretation and do not mutate
  roadway definitions.
- Packets and receipts freeze what one reconstruction supplied; they do not
  become new semantic authority merely because they were compiled.
- Handoff lifecycle events describe dispatch state and do not rewrite the
  packet or mechanism.

A future lightweight run-state object may be useful for resumable API calls,
review decisions, latency telemetry, ambiguity resolution, and provider
consent. If added later, it should be short-lived or retention-bounded,
project-scoped, non-authoritative, and clearly separate from canonical
knowledge tables. This spike does not add that object or a schema for it.

## 6. Endpoint 1: continuity/check

### Purpose

Determine whether Atlas has relevant, scope-valid, authority-valid continuity
for a current task before creating a packet or incurring provider cost.

### Proposed route

`POST /api/v1/projects/:projectId/continuity/check`

POST is appropriate because the caller submits a task body. The operation is
non-mutating: it creates no packet, receipt, handoff, finding, governance
event, mechanism, or live-state record.

### Request

```json
{
  "task": "Compare the live-entry options for a soccer favorite and identify the strongest decision rule.",
  "requestedOutput": null,
  "caseId": "case:9b647b4c-172d-4cde-9c7d-197c8647f955",
  "roadwayOverride": "broad-lock-finding",
  "tokenBudget": 800
}
```

Rules:

- `task` is exact caller text and remains controlling.
- `requestedOutput`, `caseId`, `roadwayOverride`, and `tokenBudget` are
  optional.
- The server loads the case objective; a client cannot supply a canonical case
  objective.
- A roadway override applies only to this operation.
- Supported budgets remain exactly 400, 800, and 1,600.
- Canonical IDs are never rewritten for URL safety.

### Server orchestration

1. Verify project access and optional case ownership.
2. Evaluate the Need Gate from the literal task, server-loaded project/case
   metadata, compact approved-state projections, and correction/conflict flags.
3. For `none`, return the compact explanation without a full candidate scan.
4. For `light`, return only the bounded capsule, warning, ambiguity, or
   missing-state signal; do not expand broad source text.
5. For `full`, call the existing roadway interpreter and stop on material
   ambiguity unless the caller supplied a valid current-run override.
6. Call the existing candidate-preview path only for the justified `full`
   branch.
7. Apply existing project, case, mechanism, authority, conflict, freshness,
   lineage-collapse, and protected-item eligibility rules.
8. Return a compact operational result plus references to advanced audit data.

### Proposed compact response

```json
{
  "apiVersion": "v1.7",
  "projectId": "sports",
  "caseId": "case:9b647b4c-172d-4cde-9c7d-197c8647f955",
  "literalTask": "Compare the live-entry options for a soccer favorite and identify the strongest decision rule.",
  "status": "ready",
  "interpretation": {
    "primaryRoadwayId": "roadway:...",
    "primaryRoadwayVersionId": "roadway-version:...",
    "roadwayName": "Broad Lock-Finding",
    "materialAmbiguity": null,
    "requiredLiveState": [],
    "missingLiveState": []
  },
  "continuity": {
    "hasApplicableGovernedContext": true,
    "governingMechanisms": 1,
    "requiredChecks": 5,
    "considerItems": 0,
    "provenanceRetainedForAudit": 5,
    "protectedCorrectionsSupplied": 0,
    "unresolvedConflicts": 0,
    "strongestChallenge": null
  },
  "budget": {
    "selected": 800,
    "estimatedMinimumSafe": 278,
    "estimatedFinal": 278,
    "safe": true
  },
  "effects": {
    "packetCreated": false,
    "handoffCreated": false,
    "providerCallPerformed": false,
    "authorityChanged": false
  },
  "next": {
    "canRunReconstruction": true,
    "requiredAction": null
  }
}
```

This compact result deliberately distinguishes:

- Governing mechanisms that would be supplied
- Required roadway checks
- Consider material
- Provenance retained for audit but excluded from model context

It must not report lineage ancestors as independent support, protected
corrections, or receiving-model content after an approved governing mechanism
already represents them.

### Honest non-ready states

The response status should be one of:

- `ready`
- `clarification_required`
- `missing_required_state`
- `unsafe_under_budget`
- `no_applicable_governed_context`
- `canonical_state_unavailable`

Zero applicable governed mechanisms is not a failure and must not be padded
with unapproved project memory. The result may still identify relevant
`Consider` material without claiming it can govern.

## 6A. Explicit Atlas Need Gate

`continuity/check` is not merely a ready/not-ready packet preview. It is the
Need Gate that decides how much Atlas participation is justified before full
reconstruction.

Every check returns exactly one need level: `none`, `light`, or `full`.

### `none`

Use `none` when governed continuity is unlikely to materially change the
answer, scope, constraints, or required output.

Expected behavior:

- No full candidate scan
- No packet creation
- No provider call
- A compact explanation of why Atlas context is unnecessary
- The ordinary client response proceeds without Atlas context

Examples include a self-contained factual request with no project dependency,
a simple formatting task with no applicable governed presentation rule, or a
task whose relevant current facts must come entirely from live sources.

### `light`

Use `light` when project/case metadata, one correction or conflict indicator,
a conditional preference, or a compact continuity capsule may matter, but full
packet reconstruction is not yet justified.

Expected behavior:

- A bounded project/case metadata check
- No broad source-text retrieval
- No packet creation unless a later explicit run escalates to `full`
- A suggested roadway, correction warning, ambiguity, scope warning, or
  missing-state signal may be returned

Light results may return canonical IDs and concise approved statements already
available from compact projections. They should not expand Exact source spans
or enumerate project history merely to appear useful.

### `full`

Use `full` when governed continuity can materially affect reasoning, scope,
constraints, prior corrections, conflicts, or the requested output.

Expected behavior:

- Full canonical task interpretation and candidate treatment
- Route before rank
- An optional receiving-client review gate
- Packet compilation only through a separate `reconstruction/run`

`full` still creates no packet during `continuity/check`. It establishes that
full reconstruction is justified and reports the conditions under which a run
may proceed.

### Need Gate implementation

The first implementation should be deterministic and conservative. It can use
the literal task, explicit project/case scope, compact case metadata, active
Reasoning Health, approved mechanism metadata, correction/conflict flags,
current presentation context, and roadway applicability patterns. It should
not require embeddings, a vector database, or broad Exact-source retrieval.

The compact response extends the earlier contract with:

```json
{
  "need": {
    "level": "full",
    "reasonCodes": [
      "active_case_mechanism_match",
      "approved_local_context_available"
    ],
    "explanation": "Governed case-local continuity may materially change the requested decision rule.",
    "confidenceClass": "deterministic_match",
    "escalationAllowed": true
  }
}
```

The `confidenceClass` is an implementation diagnostic, not truth, authority,
or an intelligence score.

### Need Gate risks

| Risk | Failure mode | Required mitigation |
| --- | --- | --- |
| Unnecessary Atlas invocation | A self-contained task is routed to `full`, adding latency and context noise | Prefer `none` when no project/case/mechanism dependency is found; record the triggering reason |
| Missed continuity dependency | A differently worded task is routed to `none` despite a material correction or mechanism | Use case objectives, approved mechanism metadata, conditional preferences, and correction/conflict flags before declining Atlas |
| Stale continuity | A formerly relevant rule is surfaced without current validity | Apply status, supersession, retirement, and freshness gates before `light` or `full` output |
| Over-broad retrieval | A broad project scan occurs before intent and scope are bounded | Enforce project/case, roadway, source-family, and compact-index gates before exact expansion |
| Ambiguous intent | One silent roadway choice hides materially different reconstructions | Return `light` or `full` with `clarification_required`, bounded alternatives, and no packet |

Need-level false positives cost latency, prompt space, and trust. False
negatives cost continuity and may cause repeated mistakes. Evaluation must
measure both rather than optimizing only for retrieval volume.

## 6B. Route-before-rank scaling strategy

The desired retrieval order is:

1. Need Gate
2. Project and case boundary
3. Primary roadway or bounded candidate roadways
4. Eligible source families
5. Authority, status, and freshness filters
6. Compact index or projection retrieval
7. Candidate ranking
8. Exact source expansion only for survivors
9. Stop when the minimum reliable packet is satisfied

Current V1.7 already selects a primary roadway before final treatment and
enforces project/case, authority, freshness, conflict, and lineage rules. Its
candidate preview still loads broad canonical candidate families within the
selected project—mechanisms, findings, reasoning nodes, events, source
artifacts, and live-state snapshots—before deterministic discovery and
ranking reduce them.

That scan is acceptable for the current two-project, small-dogfood corpus. It
is inspectable, deterministic, and has not required a paid embedding service.
At larger scale it will become noisy and expensive: repeated scans open more
records than a narrow task needs, increase latency, increase redundant lexical
matches, and make it harder to explain why retrieval stopped.

The first scaling improvement should not be embeddings or a vector database.
Use additive D1 projections and existing metadata first:

- Project/case/roadway/source-family keys
- Current authority and terminal-status flags
- Freshness and validity buckets
- Compact current-version statements
- Entity and deterministic mechanism-family terms
- Source ancestry and governed-descendant IDs
- Conflict/challenge/correction presence flags
- Outcome/reality-contact flags

These projections remain discovery aids. Canonical tables continue to own
truth, authority, versions, and lineage. Exact message spans or large source
artifacts are loaded only after a candidate survives the gates.

Each check and run should measure:

- Records scanned
- Records surviving each gate
- Exact sources opened
- Latency per stage
- Stopping reason
- Widening count

Valid stopping reasons include `need_none`, `light_capsule_sufficient`,
`minimum_reliable_packet_satisfied`, `clarification_required`,
`missing_required_state`, `unsafe_under_budget`, and
`no_applicable_governed_context`. Widening must be bounded and explain why the
previous scope was insufficient.

## 7. Endpoint 2: reconstruction/run

### Purpose

Compile and atomically save the smallest safe canonical reconstruction for the
current task. The endpoint returns the exact immutable packet and receipt. It
does not call a receiving model.

### Proposed route

`POST /api/v1/projects/:projectId/reconstruction/run`

### Request

The request uses the same task inputs as `continuity/check` and requires an
`Idempotency-Key` header.

```json
{
  "task": "Compare the live-entry options for a soccer favorite and identify the strongest decision rule.",
  "requestedOutput": null,
  "caseId": "case:9b647b4c-172d-4cde-9c7d-197c8647f955",
  "roadwayOverride": "broad-lock-finding",
  "tokenBudget": 800
}
```

The run must not trust a client-supplied treatment summary, case objective,
candidate list, authority, packet content, finding wording, or mechanism
wording.

### Server orchestration

1. Verify project access and canonical write authorization.
2. Validate the idempotency key.
3. Load the current canonical project and optional case.
4. Re-run interpretation and candidate treatment against current canonical
   state. A prior check is advisory, not authority.
5. Stop honestly on ambiguity, missing required state, or unsafe budget.
6. Call the existing packet compiler.
7. Save the immutable packet, packet items, and receipt atomically.
8. Return the saved snapshot without recompiling it for presentation.

### Proposed compact response

```json
{
  "apiVersion": "v1.7",
  "status": "compiled",
  "projectId": "sports",
  "caseId": "case:9b647b4c-172d-4cde-9c7d-197c8647f955",
  "packet": {
    "id": "packet:...",
    "version": 1,
    "status": "compiled",
    "tokenBudget": 800,
    "estimatedTokens": 278,
    "primaryRoadwayId": "roadway:...",
    "primaryRoadwayVersionId": "roadway-version:...",
    "content": "...exact immutable compiled content...",
    "createdAt": "..."
  },
  "summary": {
    "governingMechanismsSupplied": 1,
    "requiredChecksSupplied": 5,
    "considerItemsSupplied": 0,
    "provenanceRetainedForAudit": 5,
    "protectedCorrectionsSupplied": 0,
    "unresolvedConflictsSupplied": 0
  },
  "receipt": {
    "id": "receipt:...",
    "governanceCauses": ["governance:..."],
    "priorComparablePacketId": null,
    "historicalLimitations": [],
    "honestyStatement": "Atlas records what governed context it supplied; it does not establish outcome correctness."
  },
  "effects": {
    "packetCreated": true,
    "handoffCreated": false,
    "providerCallPerformed": false,
    "authorityChanged": false
  },
  "links": {
    "packet": "/api/v1/projects/sports/packets/packet%3A...",
    "receipt": "/api/v1/projects/sports/packets/packet%3A.../receipt",
    "inspect": "/projects/sports/inspect/packets/packet%3A..."
  }
}
```

The response is a projection of the saved canonical packet and receipt, not a
second packet representation with independent authority.

### Idempotency and failure

- Same project, task, scope, budget, actor, and idempotency key returns the
  existing run.
- Conflicting reuse fails.
- Clarification creates no packet.
- Missing required state and unsafe minimum context preserve the existing
  compiler's honest failure semantics.
- No error path returns seeded content, an England–Ghana answer, or a test
  receiver result.
- A run never performs a model-provider request.

## 8. Operational response versus audit detail

The compact response is not a loss of lineage. It is a projection designed
for the common integration path.

### Default operational response

Expose:

- Literal task
- Status and required next action
- Primary roadway
- Governing-context count
- Consider count
- Audit-only provenance count
- Conflict/challenge/correction summary
- Budget and safety
- Packet/receipt identifiers when created
- Explicit provider-call and authority-change effects

### Inspect and canonical detail

Retain:

- Every candidate and treatment reason
- Exact source/event/message lineage
- Finding and reasoning-node ancestry
- Immutable versions
- Governance events and retrieval effects
- Full Use/Consider/Exclude packet items
- Packet differences and causal explanations
- Historical limitations
- Handoff lifecycle and answer references

An appropriate compact description of the dogfood result is:

> One approved-local governing mechanism used; five provenance records
> retained for audit and excluded from receiving-model context.

It must not imply that the five ancestors were deleted, ignored, supplied as
independent evidence, or used to inflate repetition.

## 9. Inspect as the advanced console

Inspect remains the correct place for experts, reviewers, developers, and
governance operators to examine:

- Cases and boundaries
- Exact source events and spans
- Reasoning-node versions
- Findings and reviewed wording
- Mechanism scope and authority
- Governance history and rollback
- Roadway definitions
- Packet items, receipts, and comparisons
- Handoff lifecycle and provider failures
- Evaluation fixtures and results

The primary API path should link to these records rather than render all of
them inline. Work and Atlas Found remain stewardship surfaces for creating
source continuity and governing consequential meaning. Ask can become a human
debugger for the two-call API rather than the only way to use reconstruction.

## 10. Provider-neutral and BYOK-friendly handoff

Handoff remains a separate operation after reconstruction. This preserves the
boundary between free/local reconstruction and a potentially paid external
model call.

### Adapter contract

Every provider adapter should receive the same canonical input object:

```ts
type ReceivingModelDispatch = {
  providerId: string;
  modelId: string;
  originalRequest: string;
  atlasContextPacket: string;
  packetId: string;
  packetSnapshotHash: string;
  boundedInstructions: string;
};
```

Every adapter should return or fail with the same provider-neutral lifecycle:

- `pending`
- `sent`
- `completed`
- `failed`

Provider-specific response IDs and tool metadata belong in adapter metadata;
canonical request, packet, lifecycle, answer reference, and receipt semantics
remain provider-neutral.

### BYOK requirements

- Provider execution is opt-in and separate from reconstruction.
- The caller sees the provider and model before dispatch.
- A deployment may use a platform-managed key or an explicit BYOK credential
  reference.
- Raw keys must never be written to canonical D1, packets, receipts, logs,
  rendered HTML, URLs, analytics, or replay fixtures.
- A browser-delivered raw key should not become the default design. Prefer a
  deployment secret or short-lived server-side credential reference.
- Missing credentials create an honest failed or blocked state, never a
  fallback answer.
- Test receivers remain explicitly test-only and cannot appear in the
  production model list.
- Cost consent and rate limits should be explicit before any paid request.

The existing OpenAI Responses adapter can become the first implementation of
this provider contract. This spike does not alter or invoke it.

## 11. Deterministic evaluation without paid calls

Evaluation should distinguish engine correctness from receiving-model answer
quality.

### Engine evaluation

The following can be evaluated with canonical fixtures and no provider:

- Roadway selection
- Material ambiguity behavior
- Project and case isolation
- Authority and scope enforcement
- Approved-mechanism inclusion
- Irrelevant and wrong-mechanism exclusion
- Rejected/superseded/stale suppression
- Strongest-challenge retention
- Correction/conflict protection
- Lineage-aware ancestor collapse
- Packet token-budget enforcement
- Packet and receipt immutability
- Idempotent replay
- Causal governance attribution
- App/API snapshot parity

### Deterministic test receiver

A deterministic receiver may be injected only in tests. It should verify:

- The original task and Atlas packet are separate fields and roles.
- The exact saved packet hash is received.
- No recompilation occurs.
- No packet text is represented as user-authored text.
- Provider-neutral lifecycle and answer-reference plumbing work.
- Additional live retrieval remains false unless explicit fixture metadata
  says otherwise.

Its output is a transport fixture, not evidence of production provider success
or model reasoning quality.

### Replay fixture classes

1. Frozen calibration fixtures already used by Slice 4.
2. Temporary isolated-D1 service fixtures for mutations and idempotency.
3. Read-only snapshots derived from reviewed canonical packets.
4. The current Sports Engine dogfood packet as a frozen expected-result
   fixture, without updating the live dogfood records.
5. Failure fixtures for ambiguity, missing state, unsafe budget, unauthorized
   writes, provider absence, and project leakage.

Production/local dogfood D1 must not be the mutable database for automated
replay tests.

## 12. Evaluation metrics

### Invariant metrics

These are release gates and should remain exact:

| Metric | Gate |
| --- | --- |
| Cross-project governing items | 0 |
| Wrong-case approved-local items in Use | 0 |
| Rejected, retired, superseded, or stale items in Use | 0 |
| Lineage-only ancestors supplied as independent context | 0 |
| Packet-budget overruns | 0 |
| Historical packet mutations | 0 |
| Unsupported authority promotions | 0 |
| Uncaused consequential packet differences | 0 |
| Test/seeded production successes | 0 |
| Required-check retention when compilation succeeds | 100% |
| Protected applicable correction/conflict/challenge retention | 100% |
| Idempotent replay consistency | 100% |

### Calibration metrics

Track per fixture and in aggregate:

- Primary-roadway accuracy
- Material-ambiguity detection
- Governing-mechanism precision and recall
- Irrelevant-candidate exclusion rate
- Strongest-challenge retention rate
- Independent-evidence count versus ancestry count
- Provenance-collapse ratio
- Consider precision
- Token utilization and minimum-safe estimate error
- Receipt causal-link coverage
- Human correction rate
- Reconstruction determinism across repeated runs

Targets beyond constitutional invariants should be established from a larger
labeled corpus rather than invented in this documentation spike.

### Provider metrics, deferred until a real adapter is funded

- Dispatch success/failure by provider and model
- Provider latency
- Provider-reported usage and cost when available
- Packet/request role preservation
- Response/reference preservation
- Actual live-retrieval metadata

Answer correctness and product-market fit require separate evaluation. A
successful provider call does not prove either.

## 14. Authentication, isolation, and privacy

- Every route is project-scoped and verifies canonical ownership server-side.
- A non-mutating check still requires authorized access to private project
  context, even if it does not require write authority.
- Reconstruction requires the existing canonical write boundary because it
  creates an immutable packet and receipt.
- The current in-memory local write key remains a development pattern, not a
  complete multi-tenant authorization design.
- Public/demo mode remains isolated and fail-closed.
- No endpoint accepts a client-authored authority state or eligibility result.
- No cross-project content enters discovery without a future explicit
  approved transfer.
- Exact source content should not be returned in compact responses unless it
  is actually packet-eligible or explicitly requested through an authorized
  audit read.
- Provider credentials are never canonical reasoning data.

Enterprise identity, roles, SSO, and broad permissions remain outside V1.7.

## 15. OpenAPI, MCP, and compatibility

The repository's current `/openapi.json`, `/mcp`, and `/api/context` surfaces
belong to the V4.6 compatibility layer. They must not be silently relabeled as
the canonical V1.7 façade.

When the façade is implemented:

- Publish explicit V1.7 contracts for `continuity/check` and
  `reconstruction/run`.
- Generate OpenAPI and any MCP tool definitions from the same request/response
  schemas where practical.
- Keep canonical project and case IDs explicit.
- Keep idempotency, authorization, and failure schemas visible.
- Keep handoff separate and optional.
- Preserve legacy endpoints until a reviewed compatibility/deprecation plan
  exists.

An MCP tool should call the same façade handler as an HTTP request; it must not
implement its own ranking or packet builder.

## 23. Receiving-client review contract

For `full` results, a ChatGPT client, agent, or other receiving application may
insert one explicit review step after reconstruction and before answer
generation.

The receiving client verifies:

- The literal task is preserved.
- The selected roadway fits the requested reasoning mechanism.
- Required current-state categories are present and fresh.
- Stale historical facts are not presented as current.
- Project and optional case scope are correct.
- The strongest applicable challenge is preserved.
- Applicable corrections and unresolved conflicts are preserved.
- The packet is not a broad project-memory dump.
- The packet fits the current presentation requirements.

Allowed review outcomes are:

- Accept the packet.
- Request one targeted reconstruction revision.
- Ask the user one material clarification.
- Proceed without Atlas.
- Stop because required state is missing.

The client must not silently rewrite the immutable packet. A targeted revision
is a new reconstruction request with an explicit reason and, if compiled, a
new immutable packet linked to the earlier attempt where appropriate.

### Runtime review telemetry

The following are runtime telemetry and create no durable authority:

- Packet accepted or declined for this run
- Targeted revision reason code
- Clarification requested
- Proceeded without Atlas
- Missing-state stop
- Presentation mismatch
- Review latency
- Packet and run IDs

Telemetry may help evaluate retrieval calibration. It must not become a
correction, mechanism, preference, or roadmap rule automatically.

### Potential governed correction

Review feedback becomes durable only when Cody or an authorized actor makes an
explicit canonical correction or governance decision. For example, `the case
scope was wrong because this rule applies only after lineup confirmation` may
be captured as an Exact/observed correction, surfaced as one atomic finding,
reviewed, and governed. Repeated model rejection of a packet cannot validate
its own memory or silently change ranking.

## 24. Long-period effectiveness

Atlas remains useful over months or years only if it manages boundaries and
change rather than accumulating an ever-growing prompt.

### Hierarchical scope and namespaces

Use stable organization/owner, project, case, conversation, record-family,
and version boundaries. The current project/case hierarchy remains the primary
retrieval boundary. Future indexes may mirror these namespaces but cannot
override canonical scope.

### Versioning, supersession, and retirement

Mechanisms and reasoning nodes retain stable IDs with immutable versions.
Supersession and retirement remove obsolete versions from governing Use while
preserving why and when they changed. A stale correction should resolve to its
current governing version rather than repeat in every packet.

### Conflict and freshness

Approved conflicts remain explicit until conditionally reconciled or governed.
Live-state records retain observation time, validity, provider, and
supersession. Historical mechanisms may remain durable while the facts needed
to apply them must be refreshed.

### Outcome reconciliation

Outcomes and postmortems test the assumptions and mechanisms used in earlier
work. They may produce new proposals, challenges, scope revisions, or
retirements, but outcomes do not rewrite historical packets or automatically
prove a mechanism universal.

### Redundancy consolidation

Lineage-aware collapse represents one causal ancestry once in model-visible
context while preserving every ancestor for audit. Independent repetitions
from separate cases remain separate evidence. Consolidation creates proposed
supersession or compression records when consequential wording would change;
it does not destructively merge source history.

### Architectural-drift detection

Periodically compare current project/case structure with governed purposes,
scope, and active versions. Drift detection should surface bounded proposals
such as `today's Upper A substitutions no longer preserve the approved Upper A
purpose`. It cannot silently rewrite the program, Blueprint, or mechanism.

### Retention and reconstructability

Exact sources remain immutable under the applicable project retention policy.
Compressed representations reduce routine retrieval cost only when their
lineage resolves to the preserved Exact or honestly Reconstructed source.
Packets and receipts remain immutable even when their source records later
become superseded or subject to a future retention action.

### Retrieval calibration

Use Need Gate false-positive/false-negative rates, per-gate survival counts,
review outcomes, exclusion accuracy, and outcome-backed postmortems to tune
retrieval. Calibration changes remain reviewed code/configuration or governed
roadway revisions; model confidence alone cannot change authority.

### Safe background maintenance

Background maintenance may:

- Refresh compact projections and deterministic indexes
- Detect duplicate ancestry
- Flag stale live state
- Propose consolidation, supersession, retirement, or drift review
- Schedule evaluation replays
- Identify records whose retention policy needs review

It may not approve proposals, change governing versions, rewrite Exact source,
mutate packets, resolve conflicts, or promote model-generated memories.

### Failure prevention over time

| Long-period risk | Prevention |
| --- | --- |
| Endless accumulation | Need Gate, route-before-rank, retention policy, compact projections, lineage collapse, and minimum-reliable-packet stopping |
| Stale correction repetition | Current-version resolution, freshness/status filters, supersession, and packet-eligible protected-item rules |
| One-off cases becoming universal rules | Approved-local scope, explicit transfer/governance, case ownership checks, and counterevidence preservation |
| Reprocessing every transcript on every task | Immutable one-time ingestion, incremental events/checkpoints, compact indexes, and Exact expansion only for survivors |
| Prompt-cache churn | Stable versioned projections, deterministic ordering, bounded capsules, comparable packet IDs, and no recompile during reads |
| Hidden authority changes | Append-only governance events, explicit prior/new authority and scope, receipts, and no background promotion |
| Model-generated memories validating themselves | Inferred/proposed default state, Exact source lineage, Cody governance, independent evidence, and prohibition on self-approval |

## 26. Go/no-go recommendation

### Recommendation

- **Go** on the API-first simplification.
- **No-go** on rewriting the validated engine.
- **No-go** on removing or demoting the current console before façade/API
  parity is proven.
- **No-go** on paid-provider dependence for routine implementation and
  evaluation.
- **No-go** on customer or product-market-fit claims before non-sports pilots
  and direct customer discovery.

### Largest current usability risk

The current interface requires a user to understand and traverse too much of
Atlas's internal interpretation, candidate, lineage, packet, and handoff
machinery before receiving the simple value proposition: whether continuity
matters and what governed context is available. This can make a validated
engine feel more complicated than the problem it solves.

### Largest current scaling risk

Candidate preview still scans broad canonical record families within a
project before compact route/source-family gates and survivor-only Exact
expansion. That is acceptable now, but over larger multi-year corpora it will
increase latency, noise, redundant matches, and audit volume unless the
route-before-rank strategy is implemented and measured.
