# Campus Atlas V1.7 — API-first simplification spike

**Status:** Documentation-only architecture spike

**Authority:** Governed by the frozen [V1.7 implementation blueprint](V1.7_IMPLEMENTATION_BLUEPRINT.md)

**Baseline:** `main` at `75119ff67007ddbe002b856573bc74126643e180`

**Production behavior changed:** No

This spike defines a simpler operational API over the canonical V1.7 engine.
It does not change production behavior, persistence schemas, roadways, ranking,
packet compilation, handoff behavior, or any dogfood record.

The existing application remains the advanced stewardship, governance, and
inspection console. The proposed API becomes the narrow operational path for
an API sidecar, integration, pilot, or future thin client.

---

## 1. Decision record

Campus Atlas has proved the local causal loop through immutable packet
compilation. The next problem is not a missing ontology or another reasoning
feature. It is that the current product exposes too much of the internal
pipeline as the default workflow.

The approved direction is:

1. Preserve the compiled packet and existing dogfood records.
2. Do not dispatch a paid receiving-model handoff yet.
3. Add a thin `continuity/check` and `reconstruction/run` façade over the
   existing canonical services.
4. Keep Inspect as the advanced audit console rather than the main operational
   workflow.
5. Evaluate the engine with deterministic receivers and replay fixtures that
   incur no model-provider cost.
6. Keep eventual handoff provider-agnostic and friendly to bring-your-own-key
   deployments.
7. Perform one real paid provider call later when funding, credits, a
   collaborator, or a pilot makes that appropriate.

This is an interface and product-boundary simplification. It is not a rewrite
of the canonical engine.

## 3. Product boundary after the simplification

Campus Atlas remains a governed reasoning-context continuity steward.

- Cody or the caller supplies the current task.
- Atlas checks whether governed continuity is applicable.
- Atlas reconstructs an immutable, bounded context packet when asked.
- A receiving model, selected separately, reasons and answers.
- Atlas records what it supplied and why.
- Inspect exposes the full lineage and governance history.

The operational default should answer two questions:

1. **Does Atlas have legitimate context for this task?**
2. **What exact governed reconstruction should a receiving model receive?**

The default path should not require a caller to understand checkpoints,
reasoning nodes, finding versions, governance-event internals, packet-item
ancestry, or handoff lifecycle tables. Those records remain essential and
inspectable, but they are audit structures rather than the basic integration
surface.

## 4. Current canonical foundation to reuse

The façade must call the existing domain services. It must not copy their
logic into a second pipeline.

| Responsibility | Existing canonical owner | Existing API surface |
| --- | --- | --- |
| Project/session/health | `shell-service.ts` | `/api/v1/health`, `/api/v1/session`, `/api/v1/projects` |
| Conversations/messages/cases/events | `conversation-cases.ts` | Project-scoped conversation, case, event, and boundary routes |
| Checkpoints/findings | `checkpoint-service.ts` | `/checkpoints`, `/findings` |
| Governance/eligibility | `governance-service.ts` | Finding governance, rollback, eligible mechanisms |
| Roadway interpretation | `roadway-service.ts` | `/reconstruction/interpret` |
| Candidate discovery/ranking | `candidate-ranking.ts` and packet services | `/reconstruction/candidates` |
| Packet compilation/receipt | `packet-service.ts` | `/packets` and packet detail/receipt/comparison |
| Receiving-model execution | `handoff-service.ts` and `receiving-model.ts` | `/handoffs` and handoff detail/history/receipt/answer/comparison |
| Full audit reads | `inspect-service.ts` | `/inspect` and project-scoped detail routes |

The façade is an orchestration layer over these services. Canonical IDs,
authority, scope, treatment, lineage, versions, packet contents, and receipts
continue to come from the existing server-owned implementation.

## 5. Proposed operational architecture

```text
Caller task
   |
   v
continuity/check  -- no canonical mutation, no provider call
   |  interpret roadway, enforce project/case scope, preview treatment
   |  return compact eligibility + ambiguity + missing-state result
   v
reconstruction/run -- idempotent canonical write
   |  rerun against current canonical state
   |  compile packet + receipt atomically through existing services
   v
Immutable packet and causal receipt
   |
   +--> caller uses packet directly
   +--> optional later provider-neutral handoff (separate consent/cost boundary)
   +--> Inspect exposes complete lineage and audit history
```

The façade is additive. Existing project-scoped routes remain the advanced and
compatibility surface until implementation and parity tests establish that a
consumer can use the façade safely.

## 6. Endpoint 1: continuity/check

### Purpose

Determine whether Atlas has relevant, scope-valid, authority-valid continuity
for a current task before creating a packet or incurring provider cost.

### Proposed route

`POST /api/v1/projects/:projectId/continuity/check`

POST is appropriate because the caller submits a task body. The operation is
non-mutating: it creates no packet, receipt, handoff, finding, governance
event, mechanism, or live-state record.

### Request

```json
{
  "task": "Compare the live-entry options for a soccer favorite and identify the strongest decision rule.",
  "requestedOutput": null,
  "caseId": "case:9b647b4c-172d-4cde-9c7d-197c8647f955",
  "roadwayOverride": "broad-lock-finding",
  "tokenBudget": 800
}
```

Rules:

- `task` is exact caller text and remains controlling.
- `requestedOutput`, `caseId`, `roadwayOverride`, and `tokenBudget` are
  optional.
- The server loads the case objective; a client cannot supply a canonical case
  objective.
- A roadway override applies only to this operation.
- Supported budgets remain exactly 400, 800, and 1,600.
- Canonical IDs are never rewritten for URL safety.

### Server orchestration

1. Verify project access and optional case ownership.
2. Call the existing roadway interpreter.
3. Stop on material ambiguity unless the caller supplied a valid current-run
   override.
4. Call the existing candidate-preview path.
5. Apply existing project, case, mechanism, authority, conflict, freshness,
   lineage-collapse, and protected-item eligibility rules.
6. Return a compact operational result plus references to advanced audit data.

### Proposed compact response

```json
{
  "apiVersion": "v1.7",
  "projectId": "sports",
  "caseId": "case:9b647b4c-172d-4cde-9c7d-197c8647f955",
  "literalTask": "Compare the live-entry options for a soccer favorite and identify the strongest decision rule.",
  "status": "ready",
  "interpretation": {
    "primaryRoadwayId": "roadway:...",
    "primaryRoadwayVersionId": "roadway-version:...",
    "roadwayName": "Broad Lock-Finding",
    "materialAmbiguity": null,
    "requiredLiveState": [],
    "missingLiveState": []
  },
  "continuity": {
    "hasApplicableGovernedContext": true,
    "governingMechanisms": 1,
    "requiredChecks": 5,
    "considerItems": 0,
    "provenanceRetainedForAudit": 5,
    "protectedCorrectionsSupplied": 0,
    "unresolvedConflicts": 0,
    "strongestChallenge": null
  },
  "budget": {
    "selected": 800,
    "estimatedMinimumSafe": 278,
    "estimatedFinal": 278,
    "safe": true
  },
  "effects": {
    "packetCreated": false,
    "handoffCreated": false,
    "providerCallPerformed": false,
    "authorityChanged": false
  },
  "next": {
    "canRunReconstruction": true,
    "requiredAction": null
  }
}
```

This compact result deliberately distinguishes:

- Governing mechanisms that would be supplied
- Required roadway checks
- Consider material
- Provenance retained for audit but excluded from model context

It must not report lineage ancestors as independent support, protected
corrections, or receiving-model content after an approved governing mechanism
already represents them.

### Honest non-ready states

The response status should be one of:

- `ready`
- `clarification_required`
- `missing_required_state`
- `unsafe_under_budget`
- `no_applicable_governed_context`
- `canonical_state_unavailable`

Zero applicable governed mechanisms is not a failure and must not be padded
with unapproved project memory. The result may still identify relevant
`Consider` material without claiming it can govern.

## 7. Endpoint 2: reconstruction/run

### Purpose

Compile and atomically save the smallest safe canonical reconstruction for the
current task. The endpoint returns the exact immutable packet and receipt. It
does not call a receiving model.

### Proposed route

`POST /api/v1/projects/:projectId/reconstruction/run`

### Request

The request uses the same task inputs as `continuity/check` and requires an
`Idempotency-Key` header.

```json
{
  "task": "Compare the live-entry options for a soccer favorite and identify the strongest decision rule.",
  "requestedOutput": null,
  "caseId": "case:9b647b4c-172d-4cde-9c7d-197c8647f955",
  "roadwayOverride": "broad-lock-finding",
  "tokenBudget": 800
}
```

The run must not trust a client-supplied treatment summary, case objective,
candidate list, authority, packet content, finding wording, or mechanism
wording.

### Server orchestration

1. Verify project access and canonical write authorization.
2. Validate the idempotency key.
3. Load the current canonical project and optional case.
4. Re-run interpretation and candidate treatment against current canonical
   state. A prior check is advisory, not authority.
5. Stop honestly on ambiguity, missing required state, or unsafe budget.
6. Call the existing packet compiler.
7. Save the immutable packet, packet items, and receipt atomically.
8. Return the saved snapshot without recompiling it for presentation.

### Proposed compact response

```json
{
  "apiVersion": "v1.7",
  "status": "compiled",
  "projectId": "sports",
  "caseId": "case:9b647b4c-172d-4cde-9c7d-197c8647f955",
  "packet": {
    "id": "packet:...",
    "version": 1,
    "status": "compiled",
    "tokenBudget": 800,
    "estimatedTokens": 278,
    "primaryRoadwayId": "roadway:...",
    "primaryRoadwayVersionId": "roadway-version:...",
    "content": "...exact immutable compiled content...",
    "createdAt": "..."
  },
  "summary": {
    "governingMechanismsSupplied": 1,
    "requiredChecksSupplied": 5,
    "considerItemsSupplied": 0,
    "provenanceRetainedForAudit": 5,
    "protectedCorrectionsSupplied": 0,
    "unresolvedConflictsSupplied": 0
  },
  "receipt": {
    "id": "receipt:...",
    "governanceCauses": ["governance:..."],
    "priorComparablePacketId": null,
    "historicalLimitations": [],
    "honestyStatement": "Atlas records what governed context it supplied; it does not establish outcome correctness."
  },
  "effects": {
    "packetCreated": true,
    "handoffCreated": false,
    "providerCallPerformed": false,
    "authorityChanged": false
  },
  "links": {
    "packet": "/api/v1/projects/sports/packets/packet%3A...",
    "receipt": "/api/v1/projects/sports/packets/packet%3A.../receipt",
    "inspect": "/projects/sports/inspect/packets/packet%3A..."
  }
}
```

The response is a projection of the saved canonical packet and receipt, not a
second packet representation with independent authority.

### Idempotency and failure

- Same project, task, scope, budget, actor, and idempotency key returns the
  existing run.
- Conflicting reuse fails.
- Clarification creates no packet.
- Missing required state and unsafe minimum context preserve the existing
  compiler's honest failure semantics.
- No error path returns seeded content, an England–Ghana answer, or a test
  receiver result.
- A run never performs a model-provider request.

## 8. Operational response versus audit detail

The compact response is not a loss of lineage. It is a projection designed
for the common integration path.

### Default operational response

Expose:

- Literal task
- Status and required next action
- Primary roadway
- Governing-context count
- Consider count
- Audit-only provenance count
- Conflict/challenge/correction summary
- Budget and safety
- Packet/receipt identifiers when created
- Explicit provider-call and authority-change effects

### Inspect and canonical detail

Retain:

- Every candidate and treatment reason
- Exact source/event/message lineage
- Finding and reasoning-node ancestry
- Immutable versions
- Governance events and retrieval effects
- Full Use/Consider/Exclude packet items
- Packet differences and causal explanations
- Historical limitations
- Handoff lifecycle and answer references

An appropriate compact description of the dogfood result is:

> One approved-local governing mechanism used; five provenance records
> retained for audit and excluded from receiving-model context.

It must not imply that the five ancestors were deleted, ignored, supplied as
independent evidence, or used to inflate repetition.

## 9. Inspect as the advanced console

Inspect remains the correct place for experts, reviewers, developers, and
governance operators to examine:

- Cases and boundaries
- Exact source events and spans
- Reasoning-node versions
- Findings and reviewed wording
- Mechanism scope and authority
- Governance history and rollback
- Roadway definitions
- Packet items, receipts, and comparisons
- Handoff lifecycle and provider failures
- Evaluation fixtures and results

The primary API path should link to these records rather than render all of
them inline. Work and Atlas Found remain stewardship surfaces for creating
source continuity and governing consequential meaning. Ask can become a human
debugger for the two-call API rather than the only way to use reconstruction.

## 10. Provider-neutral and BYOK-friendly handoff

Handoff remains a separate operation after reconstruction. This preserves the
boundary between free/local reconstruction and a potentially paid external
model call.

### Adapter contract

Every provider adapter should receive the same canonical input object:

```ts
type ReceivingModelDispatch = {
  providerId: string;
  modelId: string;
  originalRequest: string;
  atlasContextPacket: string;
  packetId: string;
  packetSnapshotHash: string;
  boundedInstructions: string;
};
```

Every adapter should return or fail with the same provider-neutral lifecycle:

- `pending`
- `sent`
- `completed`
- `failed`

Provider-specific response IDs and tool metadata belong in adapter metadata;
canonical request, packet, lifecycle, answer reference, and receipt semantics
remain provider-neutral.

### BYOK requirements

- Provider execution is opt-in and separate from reconstruction.
- The caller sees the provider and model before dispatch.
- A deployment may use a platform-managed key or an explicit BYOK credential
  reference.
- Raw keys must never be written to canonical D1, packets, receipts, logs,
  rendered HTML, URLs, analytics, or replay fixtures.
- A browser-delivered raw key should not become the default design. Prefer a
  deployment secret or short-lived server-side credential reference.
- Missing credentials create an honest failed or blocked state, never a
  fallback answer.
- Test receivers remain explicitly test-only and cannot appear in the
  production model list.
- Cost consent and rate limits should be explicit before any paid request.

The existing OpenAI Responses adapter can become the first implementation of
this provider contract. This spike does not alter or invoke it.

## 11. Deterministic evaluation without paid calls

Evaluation should distinguish engine correctness from receiving-model answer
quality.

### Engine evaluation

The following can be evaluated with canonical fixtures and no provider:

- Roadway selection
- Material ambiguity behavior
- Project and case isolation
- Authority and scope enforcement
- Approved-mechanism inclusion
- Irrelevant and wrong-mechanism exclusion
- Rejected/superseded/stale suppression
- Strongest-challenge retention
- Correction/conflict protection
- Lineage-aware ancestor collapse
- Packet token-budget enforcement
- Packet and receipt immutability
- Idempotent replay
- Causal governance attribution
- App/API snapshot parity

### Deterministic test receiver

A deterministic receiver may be injected only in tests. It should verify:

- The original task and Atlas packet are separate fields and roles.
- The exact saved packet hash is received.
- No recompilation occurs.
- No packet text is represented as user-authored text.
- Provider-neutral lifecycle and answer-reference plumbing work.
- Additional live retrieval remains false unless explicit fixture metadata
  says otherwise.

Its output is a transport fixture, not evidence of production provider success
or model reasoning quality.

### Replay fixture classes

1. Frozen calibration fixtures already used by Slice 4.
2. Temporary isolated-D1 service fixtures for mutations and idempotency.
3. Read-only snapshots derived from reviewed canonical packets.
4. The current Sports Engine dogfood packet as a frozen expected-result
   fixture, without updating the live dogfood records.
5. Failure fixtures for ambiguity, missing state, unsafe budget, unauthorized
   writes, provider absence, and project leakage.

Production/local dogfood D1 must not be the mutable database for automated
replay tests.

## 12. Evaluation metrics

### Invariant metrics

These are release gates and should remain exact:

| Metric | Gate |
| --- | --- |
| Cross-project governing items | 0 |
| Wrong-case approved-local items in Use | 0 |
| Rejected, retired, superseded, or stale items in Use | 0 |
| Lineage-only ancestors supplied as independent context | 0 |
| Packet-budget overruns | 0 |
| Historical packet mutations | 0 |
| Unsupported authority promotions | 0 |
| Uncaused consequential packet differences | 0 |
| Test/seeded production successes | 0 |
| Required-check retention when compilation succeeds | 100% |
| Protected applicable correction/conflict/challenge retention | 100% |
| Idempotent replay consistency | 100% |

### Calibration metrics

Track per fixture and in aggregate:

- Primary-roadway accuracy
- Material-ambiguity detection
- Governing-mechanism precision and recall
- Irrelevant-candidate exclusion rate
- Strongest-challenge retention rate
- Independent-evidence count versus ancestry count
- Provenance-collapse ratio
- Consider precision
- Token utilization and minimum-safe estimate error
- Receipt causal-link coverage
- Human correction rate
- Reconstruction determinism across repeated runs

Targets beyond constitutional invariants should be established from a larger
labeled corpus rather than invented in this documentation spike.

### Provider metrics, deferred until a real adapter is funded

- Dispatch success/failure by provider and model
- Provider latency
- Provider-reported usage and cost when available
- Packet/request role preservation
- Response/reference preservation
- Actual live-retrieval metadata

Answer correctness and product-market fit require separate evaluation. A
successful provider call does not prove either.

## 14. Authentication, isolation, and privacy

- Every route is project-scoped and verifies canonical ownership server-side.
- A non-mutating check still requires authorized access to private project
  context, even if it does not require write authority.
- Reconstruction requires the existing canonical write boundary because it
  creates an immutable packet and receipt.
- The current in-memory local write key remains a development pattern, not a
  complete multi-tenant authorization design.
- Public/demo mode remains isolated and fail-closed.
- No endpoint accepts a client-authored authority state or eligibility result.
- No cross-project content enters discovery without a future explicit
  approved transfer.
- Exact source content should not be returned in compact responses unless it
  is actually packet-eligible or explicitly requested through an authorized
  audit read.
- Provider credentials are never canonical reasoning data.

Enterprise identity, roles, SSO, and broad permissions remain outside V1.7.

## 15. OpenAPI, MCP, and compatibility

The repository's current `/openapi.json`, `/mcp`, and `/api/context` surfaces
belong to the V4.6 compatibility layer. They must not be silently relabeled as
the canonical V1.7 façade.

When the façade is implemented:

- Publish explicit V1.7 contracts for `continuity/check` and
  `reconstruction/run`.
- Generate OpenAPI and any MCP tool definitions from the same request/response
  schemas where practical.
- Keep canonical project and case IDs explicit.
- Keep idempotency, authorization, and failure schemas visible.
- Keep handoff separate and optional.
- Preserve legacy endpoints until a reviewed compatibility/deprecation plan
  exists.

An MCP tool should call the same façade handler as an HTTP request; it must not
implement its own ranking or packet builder.

## 16. Observability and cost boundaries

Every façade response should disclose effects rather than imply them:

- Canonical reads performed
- Packet created or not created
- Handoff created or not created
- Provider request performed or not performed
- Authority changed or not changed
- Idempotent replay or new record
- Failure category and next required action

Logs may contain request IDs, endpoint, project ID, status, latency, selected
roadway ID/version, treatment counts, packet ID, token estimate, and failure
category. They must not contain source text, packet text, secrets, or raw
provider credentials by default.

`continuity/check` and `reconstruction/run` perform no paid model call. They
still consume local or hosted compute and D1 operations, which should be
measured separately from provider cost.

## 17. Implementation sequence after this spike

### Phase A — Additive façade

- Add the two project-scoped endpoints.
- Reuse the existing interpreter, preview, compiler, receipt, authorization,
  and idempotency services.
- Add shared typed request/response schemas.
- Add compact projection functions; do not add canonical tables.
- Add OpenAPI contract tests.
- Prove parity between façade results and existing canonical endpoints.

### Phase B — Evaluation and replay

- Add an isolated deterministic replay harness using the existing test stack.
- Freeze reviewed expected treatments before running fixtures.
- Add invariant and calibration metric output.
- Add a read-only replay for the dogfood packet snapshot.
- Keep the deterministic receiver unavailable in production.

### Phase C — Thin client and Inspect demotion

- Make the default integration/demo call the façade.
- Present compact continuity and reconstruction results first.
- Link to Inspect for full lineage rather than duplicating it.
- Preserve Work and Atlas Found as the source/governance loop.
- Do not remove advanced canonical endpoints until parity is proven.

### Phase D — Provider abstraction and BYOK

- Extract the provider-neutral adapter boundary around the existing OpenAI
  implementation.
- Add explicit cost/consent and credential-mode metadata.
- Keep raw credentials out of D1 and receipts.
- Add provider contract tests with deterministic adapters.
- Do not claim production execution from those tests.

### Phase E — One reviewed real-provider call

When funding or credits are available:

1. Select the preserved compiled packet or a reviewed successor.
2. Confirm provider, model, expected cost boundary, and credential source.
3. Dispatch once with the production adapter.
4. Verify lifecycle, response ID, answer reference, request/packet separation,
   and receipt.
5. Record the result honestly, including provider failure if it occurs.

## 18. Proposed façade acceptance criteria

The implementation following this spike is acceptable only when:

- The façade is additive and reuses canonical services.
- The exact current task remains controlling.
- Project and case ownership are server-verified.
- `continuity/check` creates no canonical record.
- `reconstruction/run` creates one immutable packet and receipt atomically.
- Material ambiguity stops before compilation.
- Missing live state and unsafe budgets fail honestly.
- One primary roadway is recorded.

- Idempotent replays do not create duplicates.
- No provider call occurs through either façade endpoint.
- No test adapter or seeded fallback appears as production success.
- Existing V4.6 and V1.7 regression contracts remain green.
- The existing dogfood packet and records remain unchanged.

## 21. Honest completion state

The local engine has proved that authentic Exact source can become a governed,
case-scoped consequence that changes a later bounded immutable reconstruction.
That is meaningful technical validation.

It has not yet proved hosted durability, a real provider execution, a complete
hosted mobile/desktop loop, customer demand, or product-market fit.

The API-first direction makes the validated engine easier to consume and
evaluate without weakening governance or paying for model calls during every
test. The simplest truthful product promise at this stage is:

> Atlas checks whether governed continuity applies and reconstructs the exact
> bounded context a later model may use. Full provenance remains available for
> audit, and provider execution is a separate optional boundary.
