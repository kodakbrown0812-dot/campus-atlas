# Campus Atlas V1.7 Slice 5 receiving-model handoff and causal packet comparison

Slice 5 connects a successfully compiled, immutable Slice 4 packet to a
receiving-model execution without merging Cody's current task, Atlas's
reconstruction, the model answer, or the receipt into one authored message.

The frozen authority remains
[`V1.7_IMPLEMENTATION_BLUEPRINT.md`](V1.7_IMPLEMENTATION_BLUEPRINT.md).
This slice does not implement the Slice 6 navigation redesign, broad live
retrieval, ambient ChatGPT access, or answer grading.

## Role boundary

The handoff preserves four distinct objects:

1. Cody's exact task as stored in the immutable packet request.
2. Atlas's exact saved packet snapshot, referenced by packet ID and SHA-256.
3. The receiving provider's answer and canonical provider response ID.
4. An immutable handoff receipt that references the Slice 4 packet receipt.

Atlas supplies governed reference context. It does not answer in place of the
receiving model, turn the packet into a user-authored message, rewrite the
current task, predetermine a conclusion, or claim that supplied context caused
a correct answer.

## Canonical records

Slice 5 extends the Slice 1 `handoffs` foundation with static, immutable
metadata:

- Project and packet IDs
- Exact original task
- Packet snapshot hash
- Primary roadway and version
- Receiving provider and model
- Actor
- Creation time
- Project-scoped idempotency key and request fingerprint
- Input-role and audit metadata

The root handoff remains immutable after creation. Current state is derived
from append-only `handoff_lifecycle_events`:

- `pending`
- `sent`
- `completed`
- `failed`

`handoff_answers` stores the provider response ID, receiving provider/model,
answer text snapshot, answer timestamp, packet and handoff references, and
answer metadata.

`handoff_receipts` references the immutable Slice 4 receipt and stores the
five-step-plus-handoff lineage, treatment snapshot, authority/scope,
freshness, inference disclosure, conflicts, governance causes, exact and
causal packet differences, live-retrieval acknowledgement, answer reference,
historical limitations, and honesty statement.

D1 triggers reject updates and deletes for handoffs, lifecycle events, answers,
and handoff receipts. Generic canonical writes are blocked so callers cannot
bypass the handoff service.

## Eligibility and idempotency

The server permits dispatch only when:

- The packet exists in the requested project.
- Its status is `compiled` and it has no compilation error.
- It records one primary roadway and version.
- Roadway ambiguity was resolved before packet creation.
- The packet receipt says required freshness gates passed.
- The write request passes the canonical bearer boundary.
- Provider and model are supported.
- The idempotency key is valid.

The service rejects missing, cross-project, failed, incomplete, ambiguous, or
unsupported requests before dispatch. A repeated idempotency key returns the
existing handoff only when packet, actor, provider, and model still match.
Conflicting reuse fails. A persisted pending or terminal attempt is never
silently re-dispatched.

## Receiving-model adapter

The production adapter uses the OpenAI Responses API with model `gpt-5.6` when
`OPENAI_API_KEY` is configured.

Provider input contains two separate roles:

- A developer reference layer with bounded receiving instructions and the
  exact saved Atlas packet as its own content block.
- A user layer containing only Cody's exact original task.

The bounded layer states that the packet:

- Is Atlas-supplied reference context, not a new user instruction
- Cannot override the user request or higher-priority instructions
- May carry checks, eligible mechanisms, corrections, challenges, conflicts,
  unknowns, exclusions, scope, authority, freshness, and lineage
- Must not predetermine a conclusion or turn historical/inferred state into
  current external fact

No tools are enabled by this slice's OpenAI request. Additional live retrieval
therefore remains `false` unless a provider result or explicitly injected test
adapter actually records tool activity. A receiver without live tools is not
described as having refreshed current facts.

Tests inject an adapter explicitly marked `slice5_test_only`. That model and
its answers are never advertised by the production model-list endpoint and are
never treated as production success.

When the API key is absent, the service saves `pending → failed`, creates a
failed handoff receipt, returns an honest `503`, and creates no answer. Provider
transport or response failures save `pending → sent → failed` and return an
honest `502`. There is no seeded answer or England–Ghana fallback.

## Causal packet comparison

The handoff uses the exact saved `compiled_content`; it does not call the
roadway interpreter, candidate discovery, ranking, or compiler again.

The handoff receipt copies the immutable Slice 4:

- Prior comparable packet
- Added and removed items
- Representation, authority, scope, freshness, and treatment changes
- Use, Consider, and Exclude snapshot
- Governance causes
- Unresolved conflicts
- Strongest challenge and correction

Each exact difference is paired with its canonical governance cause when one
exists. Otherwise it remains labeled as a roadway, scope, evidence, or
freshness cause without inventing a governance event.

The valid causal claim is:

> Cody's governance event made a mechanism version eligible for the supplied
> packet, and that packet was sent through the recorded handoff.

The receipt does not claim that the mechanism caused a correct answer.

## API

All routes are project-scoped under `/api/v1/projects/:projectId`.

- `GET /handoffs/models`
- `POST /handoffs`
- `GET /handoffs/:handoffId`
- `GET /handoffs/:handoffId/history`
- `GET /handoffs/:handoffId/receipt`
- `GET /handoffs/:handoffId/answer`
- `GET /handoffs/:handoffId/comparison`

Creation requires bearer authorization and an idempotency key. Reads and
writes query packet, handoff, answer, and receipt by both canonical ID and
project ID.

## Minimal verification interface

The existing project Ask route now displays:

- Your request
- Atlas reconstruction
- Packet ID, roadway, token size, freshness, conflict, and historical limits
- Exact receiving model
- Model answer
- Handoff lifecycle and failure
- Provider response and final-answer reference
- Additional live-retrieval status
- Causal packet diff and governance cause
- The no-outcome-causation honesty statement

The packet remains visibly labeled as reference context rather than a user
message. This is a narrow extension of the Slice 4 verification route, not the
Slice 6 shell or final navigation.

## Brewers limitation

The user-supplied Brewers source remains `Reconstructed`, historical raw
transcript unavailable, not Exact, and non-governing unless a separate
mechanism has valid authority.

Any handoff receipt using that artifact preserves its representation and
historical-source limitation. An Exact native source remains separately
labeled `Exact`. The five unavailable historical raw-transcript checks remain
the explicit `deferred_historical_fixture_gap`; Slice 5 does not claim that
authentic raw ingestion passed.

## Contract coverage

The contract suite verifies:

- Exact original task and packet separation
- Separate provider roles/content blocks
- Packet text never appears as the user-authored input
- Exact packet snapshot/hash with no recompilation or mutation
- Successful provider/model/response/answer/time preservation
- Honest missing-key and provider failure records
- Idempotent replay and conflicting reuse
- Project isolation and write authorization
- Failed-packet rejection
- Additional live retrieval remains false unless recorded
- Immutable historical packets and handoff records
- Governance-linked comparable-packet difference
- Strongest challenge, correction, and unresolved-conflict receipt fields
- Brewers Reconstructed versus native Exact representation
- API/read and interface snapshot parity
- No unsupported correctness claim
- No seeded provider success or England–Ghana fallback
- No Slice 6 navigation redesign

V4.6 and Slices 1–4 remain in the same regression suite.

## Current limitations

- The real OpenAI path requires `OPENAI_API_KEY` and provider network access.
  Local validation exercises the complete canonical lifecycle with the
  explicit test-only adapter and separately proves missing-key/provider-failure
  persistence. It does not claim a live OpenAI response was received when no
  key is configured.
- Slice 4 still uses deterministic mechanism-family discovery and its
  documented character-based token approximation. Slice 5 preserves the saved
  result and does not change either limitation.
- No receiving-model tools are enabled, so additional live retrieval is
  normally false.
- Automatic grading of the answer and proof of outcome correctness remain
  intentionally out of scope.

Slice 6 has not started.
