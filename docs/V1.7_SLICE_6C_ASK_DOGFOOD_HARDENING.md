## Final Ask route

The final route remains project-scoped:

- `/projects/:projectId/ask`

The route is part of the four-surface Work, Atlas Found, Ask, and Inspect
shell. It does not introduce another primary destination or restore the V4.6
answer-first interface.

Ask has four explicit stages:

1. **Interpret** — preserve Cody's literal request, inspect the inferred
   output, primary roadway, optional case scope, required live state, material
   ambiguity, and alternative roadways.
2. **Treat candidates** — inspect the server-owned Use, Consider, and Exclude
   treatment before a packet is created.
3. **Compile packet** — select 400, 800, or 1,600 estimated tokens and save one
   bounded immutable packet and receipt.
4. **Handoff and receipt** — keep Cody's request, Atlas's exact saved packet,
   the receiving-model answer, and the receipt visually and technically
   separate.

Material roadway ambiguity stops before candidate treatment or packet
creation. Cody may choose a temporary roadway override for that run; the
override does not modify the permanent roadway registry.

## Canonical service additions

Slice 6C adds the narrowest server reads required by the final interface.

### Candidate preview

- `POST /api/v1/projects/:projectId/reconstruction/candidates`

The endpoint uses the Slice 4 interpreter, candidate discovery, ranking,
authority, scope, evidence, conflict, freshness, and project-isolation gates.
It returns the same candidate snapshots and treatment reasons used by the
compiler without inserting a packet or receipt.

The response records:

- Interpretation and one primary roadway, or clarification required
- Use, Consider, and Exclude
- Required checks
- Protected corrections and conflicts
- Strongest applicable challenge
- Important exclusions
- Required and missing live state
- Selected token budget
- Estimated minimum-safe and final sizes
- Whether compression is likely
- `packetCreated: false`

Preview requires the existing canonical write authorization because it is an
intentional reconstruction action. It cannot promote authority from the
browser.

### Immutable history

- `GET /api/v1/projects/:projectId/packets`
- `GET /api/v1/projects/:projectId/handoffs`

The reads return project-scoped summaries of saved and failed packets,
handoffs, provider failures, answers, and receipts. Opening a history item uses
the existing immutable detail endpoint. It never recompiles a packet or
retries a handoff.

Direct links use `?packet=<canonical-id>` or `?handoff=<canonical-id>`.
Canonical IDs remain unchanged in records and API responses and are encoded
only at the URL boundary.

## Candidate treatment

Each candidate card displays:

- Statement and treatment reason
- Source type, canonical ID, and version
- Project and optional case scope
- Representation
- Authority and status
- Freshness
- Evidence strength
- Governance cause when one exists
- Counterevidence and strongest applicable challenge
- Protected role and advanced discovery metadata

Discovery signals remain discovery-only. The client does not calculate final
authority, scope eligibility, freshness, conflict resolution, or treatment.
Narrow prompts retain the Slice 4 protection against broad project-memory
dumps.

## Packet presentation

The compilation stage exposes:

- 400, 800, and 1,600 estimated-token budgets
- Minimum-safe size
- Estimated final size
- Compression state
- Missing live state
- Required checks
- Protected corrections and conflicts
- Strongest challenge
- Important exclusions
- Ready, missing-state, unsafe-under-budget, compiling, compiled, and failed
  states

A failed or unsafe packet remains an honest failed canonical record. It is not
shown as partial success and cannot proceed to handoff.

Readable packet sections and Advanced JSON are both derived from the exact
same immutable packet response. Inspection never reconstructs or edits the
saved content.

The packet comparison shows the prior comparable packet, exact item changes,
authority/scope/freshness/treatment changes, protected unchanged items, and
canonical governance causes. It describes eligibility changes, not outcome
correctness.

## Handoff presentation

The final stage keeps four objects separate:

- **Your request** — Cody's exact original task.
- **Atlas reconstruction** — the exact immutable saved packet, labeled as
  Atlas-supplied reference context and not a user instruction.
- **Model answer** — the receiving provider's separate answer or an honest
  absence/failure.
- **Receipt** — the immutable audit of what Atlas supplied and why.

The interface shows provider/model, lifecycle, timestamps, answer reference,
additional live retrieval, prior packet, causal difference, governance cause,
conflicts, strongest challenges, corrections, and historical limitations.

Only models returned by the backend with `production: true` are selectable.
The test adapter and `atlas-test-receiver-v1` are never offered by the
production interface. Missing `OPENAI_API_KEY` or provider failure creates and
displays an honest failed handoff record and no answer.

Retry creates a new attempt with a new idempotency key. It does not mutate or
redispatch the terminal attempt.

## Project and session behavior

The centralized Slice 6A in-memory write authorization remains outside the
project-scoped shell subtree. Switching projects preserves the authorized
session but remounts every Ask-local selection and draft:

- Literal task
- Interpretation and override
- Candidate preview
- Packet budget and result
- Handoff and answer
- Selected history item
- Error and notice

All canonical reads and writes continue to verify the project in D1.
Cross-project semantic similarity cannot populate the UI.

Read-only sessions may inspect existing canonical records. Reconstruction,
packet compilation, and handoff actions remain disabled until the centralized
session is authorized. No key is persisted in browser storage, rendered HTML,
or logs.
