# Campus Atlas V4.6 architecture audit

Date: 2026-07-26  
Restore point: `bc48824ffd02a0a3ff27e7c9446534c145c6c7e9`  
Protection branch: `v1.7-slice-0-protection`

## Purpose and scope

This document records the V4.6 baseline that V1.7 will migrate. It describes what the repository actually implements, distinguishes persisted behavior from derived and seeded behavior, and identifies boundaries that should remain stable during migration.

Slice 0 does not introduce V1.7 product semantics. In particular, it does not add canonical V1.7 tables, conversation ingestion, Atlas Found, roadways, or new governance rules.

## Runtime architecture

Campus Atlas is a TypeScript and React 19 application using Next.js 16 App Router conventions. `vinext` runs the Next-compatible application through Vite 8 and produces an ESM Cloudflare Worker. The Worker is the HTTP entry point for the rendered app, Atlas APIs, MCP, OpenAPI, image optimization, and D1 access.

The principal runtime layers are:

1. `app/page.tsx`: one client-side React application containing navigation, project views, UI workflows, local state transitions, and API synchronization.
2. `app/v46-data.ts`: V4.6 domain types, project definitions, seeded Amy Campus records, and the conversion from UI records to API retrieval nodes.
3. `worker/index.ts`: Cloudflare Worker request routing and Vinext fallback.
4. `worker/atlas-state.ts`: serialized workspace state persistence in D1.
5. `worker/atlas-actions.ts`: deterministic packet compilation, API/MCP contracts, governed sidecar writes, and persisted external receipts.
6. `worker/ai-structure.ts`: optional OpenAI Responses API capture structuring with deterministic validation and an explicit seeded fallback.

### Framework and language

- TypeScript with strict compiler settings
- React 19 client components
- Next.js 16 App Router compatibility through Vinext
- Vite 8
- Tailwind CSS 4 through PostCSS, plus a large application stylesheet
- ESLint 9 with Next.js core-web-vitals and TypeScript rules

`build/sites-vite-plugin.ts` copies the Sites manifest and Drizzle migrations into `dist/.openai` after a successful build. `dist/server/index.js` is the validated Worker entry point.

## State and persistence

### D1 storage model

V4.6 uses one D1 table:

```text
atlas_state
  id          TEXT PRIMARY KEY
  payload     TEXT NOT NULL
  updated_at  TEXT NOT NULL
```

The `payload` is the full serialized `AtlasState`. Cases, evidence, knowledge, blueprint rules, reviews, connections, activities, context packets, proof baseline, and retrieval nodes are not separate database entities.

This serialized document is the current persistence boundary, not a normalized canonical data model. Slice 1 should treat schema version `46` and existing payloads as migration inputs.

### Private workspace mode

Without `CAMPUS_ATLAS_PUBLIC_DEMO=true`, `/api/state` reads and writes the fixed D1 row `primary-campus`. Access control is expected to be supplied by the hosting policy; the state route has no application-level user partition.

### Public demo mode

With `CAMPUS_ATLAS_PUBLIC_DEMO=true`, the state layer:

- accepts only IDs matching `demo-[a-z0-9]{20,40}`;
- resolves an ID from `x-atlas-workspace`, `workspaceId`, or a secure cookie;
- creates an opaque ID when needed;
- stores each demo workspace in a separate D1 row;
- does not fall back to the private workspace;
- returns a secure, HTTP-only, same-site cookie for a newly created workspace.

An opaque workspace key is isolation by possession, not authenticated identity. Public demo state must never contain secrets or sensitive records.

### Browser load/save flow

1. The client initializes immediately with `makeSeedState()`.
2. After mount it calls `GET /api/state`.
3. If the response contains `schemaVersion: 46`, the persisted state replaces the initial seed.
4. If state is missing, incompatible, or unavailable, the client retains a fresh seed.
5. Once hydrated, every state change schedules `POST /api/state?replace=true` after 420 ms.
6. In demo mode, the workspace ID is sent in both the state and `x-atlas-workspace`.

The browser posts the complete state document. The backend validates payload size but does not independently validate every governance transition in a replacement snapshot.

### Merge behavior

`POST /api/state` without `replace=true` merges selected record arrays by ID. `replace=true` replaces the stored payload. The current UI uses replacement writes. Sidecar action handlers load the current snapshot, add records, and save a new full snapshot.

## Ownership and authority

### Backend-persisted behavior

- Full `AtlasState` snapshots in D1
- Session-scoped public demo workspaces
- Context packet history, capped by the backend at 25 packets
- Sidecar-created cases, evidence, outcomes, proposed learning, reviews, activities, nodes, and connections
- External action receipts and idempotency keys
- Deterministic packet compilation and inclusion/exclusion receipts
- API write authentication and fail-closed behavior
- OpenAPI and MCP contracts

Persisted does not always mean independently governed by the backend. Browser replacement snapshots are persisted as supplied.

### Frontend-derived behavior

- Global and project navigation
- Active project/tab/selection state
- Case workflow presentation
- Most interactive review decisions and their coordinated record updates
- Browser capture record construction
- Blueprint approval transitions initiated in the UI
- Graph filtering and inspection
- Direct natural-language response text shown above an Atlas packet
- Transient transition receipts and toast notifications
- `nodes` regenerated from cases, evidence, and knowledge by `normalizeState`

These behaviors are meaningful V4.6 product behavior, but most are implemented as client-side state transformations before the resulting snapshot is saved. They are not a safe future authority boundary by themselves.

### Backend-enforced governance

Sidecar write routes enforce:

- bearer authorization when a write key is configured;
- required fields;
- idempotency keys;
- proposed/non-authoritative status for new candidates;
- no automatic promotion;
- target existence for outcomes and case events;
- an allowed event-type set;
- bounded confidence values for case events;
- preserved receipts.

Packet compilation enforces approved status, active project matching, domain/mechanism fit, explicit transfer scope, token budget, and explained exclusions.

### Seeded behavior

`app/v46-data.ts` contains the Amy Campus V4.6 demonstration corpus:

- four project definitions;
- example cases;
- evidence records;
- approved and pending knowledge;
- blueprint rules;
- review items;
- graph connections;
- activity history.

`makeSeedState()` is used when no compatible persisted state can be loaded and by Reset Demo.

`worker/atlas-actions.ts` also contains fallback nodes and fallback blueprints. These allow packet APIs to return a labeled V4.6 demonstration corpus when D1 has no nodes. This fallback is separate from the full client seed and should not be expanded as V1.7 behavior.

`worker/ai-structure.ts` returns a seeded capture proposal when `OPENAI_API_KEY` is absent or the live request/validation fails. Its receipt labels the mode as `seeded_demo`; it must not be represented as a live model result.

### Fixture-only behavior

- `tests/rendered-html.test.mjs` uses an in-memory D1 double and a test seed tailored to packet/retrieval assertions.
- `examples/d1/` is starter/reference code and is not routed by the application.
- The source ZIP archives are not executed.

### Unsupported or not established

- Conversation ingestion
- Live-source discovery or current-fact retrieval
- V1.7 Atlas Found or roadway concepts
- Normalized canonical tables for cases, evidence, governance, lineage, or receipts
- Server-authoritative validation of every browser governance transition
- Multi-user authorization inside a private workspace
- Per-project storage isolation at the database row level
- Background jobs, queues, or event replay
- Production use of `app/chatgpt-auth.ts` in the root route
- A supported migration path between arbitrary `AtlasState` schema versions

### MCP surface

V4.6 reports MCP server version `4.6.0` and exposes seven tools:

1. `atlas_build_context_packet`
2. `atlas_get_project_blueprint`
3. `atlas_retrieve_precedents`
4. `atlas_get_receipt`
5. `atlas_capture_candidate`
6. `atlas_record_outcome`
7. `atlas_submit_case_event`

Read and write tools are separated. Write tools share the bearer and idempotency boundaries used by the HTTP routes.

## Project isolation

The UI filters cases, evidence, knowledge, rules, activities, and selected records by `activeProject`. Campus review items can appear in a target project only when `targetProject` matches.

Packet compilation normalizes the requested project and selects authoritative durable knowledge only when the node belongs to that project. Cross-project pathways require an explicit `transfers` or `campus` retrieval scope and never make an unapproved source record target-project authority.

Important limits:

- `/api/state` returns the entire workspace, not a project projection.
- All projects share one serialized workspace row.
- Project isolation depends on application filters and deterministic packet logic, not D1 row-level separation.
- Public demo workspace isolation and project isolation solve different problems.

## Mobile baseline

At widths below 980 px, the desktop sidebar is replaced by a fixed four-item bottom navigation. A separate floating Capture action remains available. Below 680 px, project tabs and counts become horizontally scrollable; work, review, ledger, blueprint, graph, packet, and modal layouts collapse to one column. The existing regression suite protects the presence of Home, Projects, Review, Atlas, Ask, Capture, Work, Evidence, and Blueprint on mobile.

No visual redesign is part of Slice 0.

## Migration risks

1. **Authority is split.** Existing UI governance transitions are primarily client-authored, while sidecar writes have backend checks. V1.7 must not mistake persistence for server authority.
2. **One serialized aggregate.** Every domain is coupled inside one replaceable JSON payload. Partial failures, concurrent writers, and migrations can overwrite unrelated changes.
3. **Dual seeded corpora.** The client seed and Worker fallback nodes/blueprints can diverge.
4. **Derived node duplication.** `nodes` duplicates cases/evidence/knowledge and is regenerated by the browser but also written by backend actions.
5. **Packet-history race.** The backend appends up to 25 packets, while the browser also appends a packet locally and later replaces the full state with an eight-packet window.
6. **Project isolation is logical.** It is enforced by filtering and retrieval rules, not separate storage or authenticated authorization.
7. **Identifier normalization is heuristic.** Free-form project names map into a small set of keys.
8. **Fallback on persistence failure.** Read failures can silently present seeded content; the UI indicates save error later, but initial seed availability is not proof of D1 health.
9. **Large central files.** Most UI behavior is in one component and most backend behavior is in one Worker module, increasing change collision risk.
10. **Contract drift.** README language, OpenAPI coverage, MCP tool counts, client packet types, and backend packet shapes must remain synchronized.
11. **Package metadata drift.** `package.json` identifies `rebar-decision-memory`, while the existing lockfile root still identifies the original `site-creator-vinext-starter`; dependency resolution works, but product/package naming should be reconciled intentionally outside this protection slice.

## Recommended V1.7 migration boundaries

- Preserve the V4.6 restore commit and keep migration work off `main`.
- Read schema-46 snapshots as immutable migration inputs before changing storage.
- Define backend authority explicitly before moving any client governance transition.
- Keep the packet compiler, receipt explanations, scope boundaries, and fail-closed writes behaviorally protected.
- Separate demo seeds from production-empty-state behavior without deleting the V4.6 fixtures until migration validation is complete.
- Migrate one bounded domain at a time; do not replace the whole `AtlasState` and UI simultaneously.
- Maintain an adapter from new canonical records to the existing V4.6 UI until equivalent behavior is demonstrated.
- Keep current external facts outside durable Atlas authority unless a live source and provenance are preserved.
- Treat cross-project reconstruction and target-project authority as separate concepts.
- Add schema-versioned migrations and concurrency strategy before introducing multiple independent writers.
