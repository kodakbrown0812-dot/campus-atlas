# Campus Atlas V1.7 Slice 1 canonical foundation

Slice 1 adds normalized D1 records beside the existing V4.6 `atlas_state`
snapshot. It does not migrate user data, change V4.6 governance, or switch the
current interface to canonical reads.

## Boundaries

- `worker/atlas-state.ts` remains the V4.6 compatibility and rollback path.
- `db/schema.ts` and `drizzle/0001_bored_sage.sql` define the additive V1.7
  foundation.
- `worker/canonical-records.ts` owns project-scoped canonical record access.
- `worker/legacy-classification.ts` records the required migration
  classification vocabulary without granting legacy records authority.
- `/api/v1/projects/:projectId/records/:recordType[/:recordId]` is the
  deliberately narrow Slice 1 contract. It supports scoped reads and basic
  creation only; writes use the existing fail-closed bearer boundary. Later
  slices add domain-specific services and transactions.

## Canonical tables

Source and continuity:

- `projects`
- `conversations`
- `messages`
- `events`
- `cases`
- `case_event_attachments`

Reasoning and governance:

- `reasoning_nodes`
- `reasoning_node_versions`
- `findings`
- `finding_versions`
- `mechanisms`
- `mechanism_versions`
- `governance_events`
- `roadways`
- `roadway_versions`

Reconstruction:

- `packets`
- `packet_items`
- `receipts`
- `handoffs`

All child tables include `project_id` so API reads can enforce project scope
without trusting a client-side filter. Immutable version tables use
`supersedes_version_id`. Governance events and handoffs use project-scoped
idempotency keys. Source and changing-state records include temporal fields
where they are applicable.

## Legacy compatibility

`atlas_state` remains readable and writable by existing V4.6 routes. The new
tables do not mirror browser snapshot mutations, and the current UI does not
read from them. This prevents accidental dual authority while later slices are
under construction.

Legacy records must be classified before migration as one of:

- verified canonical history
- re-ingestion source
- calibration fixture
- unverified proposal
- UI-only state
- duplicate
- obsolete historical state

An old `Approved` label is not sufficient to create V1.7 authority.

## Known dual-state risks

- V4.6 and V1.7 records coexist until canonical services replace each workflow.
- The generic Slice 1 API is scaffolding, not the final domain API.
- Foreign keys enforce identity relationships, while service-level project
  checks enforce ownership; all later services must retain both.
- Migration order matters because D1 foreign keys are enabled.
- Existing packets and receipts remain in legacy snapshots until explicitly
  classified and migrated.

Before the V1.7 cutover, the app must stop new legacy writes for conversations,
findings, governance, mechanisms, packets, and receipts. Two writable
authorities must not remain indefinitely.
