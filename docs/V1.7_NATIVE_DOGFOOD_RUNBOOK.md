# Campus Atlas V1.7 native exact-source dogfood runbook

## Status

This is the manual acceptance procedure for the first authentic V1.7 native
conversation. It is ready to run but has **not yet been executed**.

Do not seed this proof, reuse a fixture answer, reconstruct a missing
conversation, or claim completion from automated tests alone.

The historical Brewers artifact remains a separate `Reconstructed` proof
layer. It cannot satisfy this native `Exact` source test.

## Prerequisites

- A migrated canonical D1 environment
- One test project owned by Cody
- Canonical write authorization
- A supported production receiving model
- `OPENAI_API_KEY` when a real handoff is part of the run
- Desktop and mobile access to the same hosted environment
- A second browser session for persistence/parity verification
- A legitimate task that does not repeat a desired mechanism merely to force
  retrieval

Record the environment, deployment/version, project ID, actor, start time, and
receiving provider/model before beginning. Never record secret values.

## Evidence record

Create one release evidence note containing:

- Deployment URL and version/commit
- Project ID
- Conversation ID
- Case ID
- Message IDs and hashes
- Event/source-span IDs
- Checkpoint ID
- Finding and finding-version IDs
- Governance event ID
- Mechanism and governing-version IDs when created
- Pre-governance packet and receipt IDs
- Post-governance packet and receipt IDs
- Handoff ID
- Provider response and answer reference
- Desktop and mobile verification time
- Second-session verification time
- Failures, retries, and unresolved limitations

## Phase 1 — Start an authentic native conversation

1. Open **Work** in the selected canonical project.
2. Select **Start Atlas conversation**.
3. Enter a real title and objective.
4. Save and wait for canonical confirmation.
5. Record the conversation ID.
6. Create or select one bounded active case.
7. Record the case ID and verify it is the only active case for the
   conversation.

Confirm through the app and API:

- Conversation project ID
- Active case ID
- Exact title/objective
- Creation timestamp
- Refresh restores the same records

## Phase 2 — Preserve exact messages

Conduct a real short reasoning exchange in Atlas. Use original text written
during this run.

For every message verify:

- Exact content
- Authorship
- Sequence
- Timestamp
- Content hash
- Canonical message ID
- Refresh persistence

Append at least one user message and one receiving-model or imported assistant
response through the supported native path. Do not edit a preserved message
after confirmation.

Verify the same message list through the project-scoped API. A mismatch in
content, authorship, sequence, timestamp, hash, or ID is a release blocker.

## Phase 3 — Exact source lineage

Create or inspect meaningful events from the native messages.

For every event used later:

- Confirm `Exact` representation
- Confirm canonical message ID
- Confirm source-span start and end
- Follow the UI link to the exact message and span
- Confirm URL encoding did not change the canonical ID
- Confirm the API returns the same event and source span

Do not accept an invented, cleaned, or approximate span.

## Phase 4 — Analyze now

1. Run **Analyze now** from the active case.
2. Observe the real stages: preparing events, identifying candidate
   structure, selecting consequential nodes, checking missing state/conflict,
   and creating findings.
3. Record the checkpoint ID.

Verify:

- Trigger and case
- Events considered
- Candidate, selected, and omitted counts
- No more than seven selected nodes
- Reasoning Health before and after
- Missing state and ambiguity
- Zero findings is allowed and must not be presented as failure or fabricated
  success

If zero findings are created, continue the authentic conversation until a
consequential atomic proposal can truthfully be surfaced, then run another
checkpoint. Record both checkpoints.

## Phase 5 — Review and govern one consequence

Open one atomic Atlas Found proposal.

Verify the review displays:

- Atlas's original wording
- Cody's reviewed wording
- Exact wording difference
- One proposed consequence
- Scope, conditions, and exclusions
- Strongest support
- Strongest challenge
- Missing evidence and uncertainty
- Exact source lineage

Revise the wording or scope when appropriate. Approve Cody's final reviewed
version only after the explicit confirmation language matches the intended
retrieval effect.

Record:

- Finding and version
- Governance event ID
- Prior/new authority
- Prior/new scope
- Exact retrieval effect
- Mechanism/version when created

Confirm through app and API that only Cody's final wording and scope govern.

## Phase 6 — Prove governance changes a later packet

Use one legitimate later task whose reasoning mechanism is applicable without
copying the approved mechanism into the prompt.

For the comparable proof:

1. Preserve or create the pre-governance packet when available.
2. Interpret the later task.
3. Confirm exactly one primary roadway.
4. Resolve any material ambiguity explicitly.
5. Inspect Use, Consider, and Exclude.
6. Confirm the strongest applicable challenge remains visible.
7. Compile the post-governance packet with a supported budget.
8. Record packet and receipt IDs.

Verify:

- The literal request remains controlling
- Candidate treatment is server-owned
- Project and case scope are correct
- The governed consequence becomes eligible only because of the recorded
  governance event
- The prior comparable packet is linked
- Exact additions/removals/authority/scope/freshness/treatment changes appear
- Required correction, conflict, and strongest challenge survive compression
- No broad memory dump appears for a narrow task
- The receipt does not claim the packet caused correctness

## Phase 7 — Receiving-model handoff

Before sending, verify:

- Packet is compiled and immutable
- Packet belongs to the active project
- Provider/model is a supported production choice
- Your request and Atlas reconstruction are separate
- Atlas context is labeled as reference, not a user instruction
- Historical limitations and conflicts remain visible

Send the exact saved packet.

Verify:

- Handoff ID and lifecycle
- Provider/model and timestamp
- Exact packet snapshot/hash
- Original task unchanged
- Provider response ID and answer reference when successful
- Additional live retrieval is false unless actual tool metadata proves it
- Answer is visually separate from request, packet, and receipt
- Failure creates an honest failed handoff and no seeded answer

A test-only adapter is not acceptable evidence for the production handoff
gate.

## Phase 8 — App/API parity

For each consequential record below:

1. Read it in the app.
2. Read it through the project-scoped API.
3. Compare ID, version, project, case, scope, authority, status, and retrieval
   effect.
4. Refresh the browser and compare again.
5. Open a second session and compare again.

Cover:

- Conversation and messages
- Active case
- Events and source spans
- Checkpoint and findings
- Reviewed finding version
- Governance event and mechanism
- Pre/post packets and receipts
- Handoff lifecycle
- Answer reference or honest failure

Any mismatch is a release blocker.

## Phase 9 — Mobile parity

Repeat the operational loop on mobile:

- Select project
- Continue the native conversation
- Inspect active case and Reasoning Health
- Run Analyze now
- Open and review the finding
- Edit wording/scope and govern
- Submit the later task
- Inspect roadway and Use/Consider/Exclude
- Compile and inspect the packet
- Send the handoff
- Inspect answer/failure, diff, and receipt
- Return to the conversation

Confirm there is no horizontal page overflow and no desktop-only required
action. Mobile must retain scope, authority, challenge, and retrieval-effect
details.

## Completion criteria

The native proof passes only when:

- Exact source content and lineage are preserved
- One bounded case carries the reasoning pathway
- Analyze now selects at most seven nodes
- An atomic finding is governed using Cody's final wording
- Retrieval eligibility changes
- A later legitimate task selects the correct roadway
- Use, Consider, and Exclude are inspectable
- Governance causes an exact comparable-packet change
- Strongest challenge or uncertainty remains
- The exact saved packet is handed off separately from the task
- The receipt identifies the governance event
- App/API, refresh, second-session, desktop, and mobile parity pass
- No fixture, seeded success, ambient ChatGPT claim, or causation claim is used

Until the evidence record is completed, report this dogfood gate as pending.
