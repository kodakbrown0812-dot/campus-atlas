## Phase 1 — Start an authentic native conversation

1. Open **Work** in the selected canonical project.
2. Select **Start Atlas conversation**.
3. Enter a real title and objective.
4. Save and wait for canonical confirmation.
5. Record the conversation ID.
6. Create or select one bounded active case.
7. Record the case ID and verify it is the only active case for the
   conversation.

Confirm through the app and API:

- Conversation project ID
- Active case ID
- Exact title/objective
- Creation timestamp
- Refresh restores the same records

## Phase 2 — Preserve exact messages

Conduct a real short reasoning exchange in Atlas. Use original text written
during this run.

For every message verify:

- Exact content
- Authorship
- Sequence
- Timestamp
- Content hash
- Canonical message ID
- Refresh persistence

Append at least one user message and one receiving-model or imported assistant
response through the supported native path. Do not edit a preserved message
after confirmation.

Verify the same message list through the project-scoped API. A mismatch in
content, authorship, sequence, timestamp, hash, or ID is a release blocker.

## Phase 3 — Exact source lineage

Create or inspect meaningful events from the native messages.

For every event used later:

- Confirm `Exact` representation
- Confirm canonical message ID
- Confirm source-span start and end
- Follow the UI link to the exact message and span
- Confirm URL encoding did not change the canonical ID
- Confirm the API returns the same event and source span

Do not accept an invented, cleaned, or approximate span.

## Phase 4 — Analyze now

1. Run **Analyze now** from the active case.
2. Observe the real stages: preparing events, identifying candidate
   structure, selecting consequential nodes, checking missing state/conflict,
   and creating findings.
3. Record the checkpoint ID.

Verify:

- Trigger and case
- Events considered
- Candidate, selected, and omitted counts
- No more than seven selected nodes
- Reasoning Health before and after
- Missing state and ambiguity
- Zero findings is allowed and must not be presented as failure or fabricated
  success

If zero findings are created, continue the authentic conversation until a
consequential atomic proposal can truthfully be surfaced, then run another
checkpoint. Record both checkpoints.

## Phase 5 — Review and govern one consequence

Open one atomic Atlas Found proposal.

Verify the review displays:

- Atlas's original wording
- Cody's reviewed wording
- Exact wording difference
- One proposed consequence
- Scope, conditions, and exclusions
- Strongest support
- Strongest challenge
- Missing evidence and uncertainty
- Exact source lineage

Revise the wording or scope when appropriate. Approve Cody's final reviewed
version only after the explicit confirmation language matches the intended
retrieval effect.

Record:

- Finding and version
- Governance event ID
- Prior/new authority
- Prior/new scope
- Exact retrieval effect
- Mechanism/version when created

Confirm through app and API that only Cody's final wording and scope govern.

5. Inspect Use, Consider, and Exclude.

Verify:

- The literal request remains controlling

- The governed consequence becomes eligible only because of the recorded
  governance event
- The prior comparable packet is linked
- Exact additions/removals/authority/scope/freshness/treatment changes appear
- Required correction, conflict, and strongest challenge survive compression
- No broad memory dump appears for a narrow task
- The receipt does not claim the packet caused correctness
