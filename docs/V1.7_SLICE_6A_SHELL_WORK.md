# Campus Atlas V1.7 Slice 6A shell and Work

Slice 6A is the first bounded implementation subdivision of Slice 6. It
replaces the V4.6 decorative root and project navigation with the final
four-surface application shell, makes canonical Work and conversations the
default operational experience, and derives Reasoning Health from canonical
records.

The frozen authority remains
[`V1.7_IMPLEMENTATION_BLUEPRINT.md`](V1.7_IMPLEMENTATION_BLUEPRINT.md).
Slice 6A does not add product scope. It does not implement the final Atlas
Found, governance, Inspect, Contextual Add, Ask, packet, receipt, or handoff
experiences assigned to Slice 6B and Slice 6C.

## Final shell boundary

Every project-scoped route is wrapped by one application shell with exactly
four primary destinations:

- Work
- Atlas Found
- Ask
- Inspect

Desktop uses a persistent sidebar. Mobile uses a compact header and bottom
navigation with the same labels. The project selector is canonical and changes
the project segment in the route. That route change unmounts the prior project
tree, clearing selected records and drawers instead of carrying project-local
state into the next project.

Atlas Found and Ask continue to use their proven Slice 3–5 verification
experiences inside the new shell. Inspect is an honest placeholder until the
canonical tabs are implemented in Slice 6B. Slice 6A does not present these
surfaces as complete.

## Root and Work

The root reads canonical health and canonical projects. It restores the most
recently active canonical project into `/projects/:projectId/work`. When no
project exists, it shows an honest empty state. When D1 is unavailable, it
shows an unavailable state and does not substitute seeded state.

Work reads `/api/v1/projects/:projectId/work` and provides:

- Continue working
- Active conversations
- Needs decision
- Needs outcome
- Deferred
- Recently changed packets

The transcript, active case, Reasoning Health, last meaningful change, pending
finding count, and next action are derived from canonical records. Work also
provides the bounded Slice 6A entry points for creating a native conversation
and importing exact or reconstructed source material through the existing
Slice 2 services.

The former `/projects/:projectId/conversations` index redirects to Work.
Direct canonical conversation links remain supported.

## Canonical shell reads

Slice 6A adds narrow read contracts:

- `GET /api/v1/health`
- `GET /api/v1/session`
- `GET /api/v1/projects`
- `GET /api/v1/projects/:projectId/work`

The health contract tests D1 directly and reports:

- canonical state availability
- canonical D1 persistence
- project count
- explicit fixture mode
- explicit seeded-fallback status
- public-demo mode
- check time

Failures return a non-success status with `canonicalState: unavailable`,
`fixtureMode: false`, and `seededFallback: false`.

The session contract reports the current actor, workspace mode, configured and
authorized write state, and read-only state. It never returns the configured
action key.

Project and Work reads are scoped by canonical project ID. Work records are
joined and queried inside that scope; semantic similarity is not involved.

## Session and write authorization

The browser uses one React session provider for the canonical write key. The
key exists only in component memory:

- It is not stored in local storage or session storage.
- It is not placed in a URL.
- It is not rendered after entry.
- It is not logged.
- It is verified against the canonical session endpoint.
- Canonical writes still require the server bearer boundary.

Refreshing the browser intentionally returns to read-only mode. The desktop
shell exposes the authorization control in its session panel. Mobile exposes
the same control in a bounded sheet. Unconfigured, unauthorized, and
authorized states remain distinct.

This is a local/private-workspace session pattern, not an ambient ChatGPT
authorization claim.

## Canonical conversation workspace

The conversation workspace keeps the immutable transcript primary and uses the
existing Slice 2–3 canonical APIs for:

- Appending user or assistant messages
- Preserving exact content, role, sequence, timestamp, and content hash
- Inspecting import provenance and raw source artifacts
- Creating and selecting the active case
- Reading exact source references
- Running Analyze now as a checkpoint

A message appears in the transcript only after the server confirms the write.
A failed write remains visible as a failure and is not described as preserved.
Imported and native conversations share the same transcript display.
Reconstructed source artifacts remain visibly `Reconstructed`.

Analyze now displays preparation, candidate selection, conflict and
missing-state checks, finding creation, completion, partial, and failed states.
Its result shows the trigger, case, event and candidate counts, selected and
omitted nodes, Reasoning Health before and after, missing state, ambiguity,
findings, and retrieval effect. Zero findings is a valid successful result.

## Reasoning Health

Reasoning Health is derived server-side from the active canonical case,
attached events, current finding versions, and the latest checkpoint. The six
states are:

- Forming
- Missing information
- Awaiting decision
- Awaiting outcome
- Awaiting governance
- Conflict

Each result includes the canonical cause, a source link, the recommended next
action, latest checkpoint summary, and pending finding count. The badge is not
editable and does not claim truth, confidence, importance, or predicted
success.

## Legacy retirement

The V1.7 root and new Slice 6A actions do not read or write `AtlasState`.
Specifically:

- The root no longer loads `makeSeedState`.
- The root no longer reads or writes `/api/state`.
- Project selection and restoration use canonical project records.
- New conversations, imports, messages, active cases, and checkpoints use
  canonical Slices 2–3 services.
- Canonical D1 failure never falls back to seeded production content.
- The V4.6 England–Ghana corpus remains only for compatibility, rollback, and
  the existing V4.6 regression contracts.

Legacy `AtlasState` remains in the repository for read-only historical and
regression coverage. It is not a second writable authority for the new V1.7
interface.

## Empty and failure states

Slice 6A distinguishes:

- Loading
- Connected canonical D1
- No canonical project
- No active conversation
- Read-only or unauthorized session
- Canonical state unavailable
- Persistence failure
- Conversation creation or import failure
- Message save failure
- Active-case failure
- Checkpoint failure or partial result

Every failure states what remains valid and what the user can do next. None is
replaced with seeded success.

## Regression and contract coverage

The automated suite covers:

- Canonical health, projects, session, and project-scoped Work reads
- No returned secret
- Authorized and unauthorized session states
- Project isolation
- Derived Reasoning Health
- Honest D1 failure
- Root restoration without `AtlasState` or seeded fallback
- Exactly four primary destinations and mobile parity
- Canonical-only Work and conversation mutations
- V4.6 compatibility data no longer owning the V1.7 root
- Existing V4.6 and Slices 1–5 behavior

The append-only Slice 5 handoff lifecycle is read in insertion order. This
prevents fixed or provider-supplied timestamps from reordering `pending`,
`sent`, and terminal events while preserving every event.

The unavailable verbatim historical Brewers transcript remains five explicitly
deferred fixture checks. The Brewers reconstruction remains
`Reconstructed`; Slice 6A does not promote it to Exact.

## Slice 6B and Slice 6C remain

Slice 6B remains responsible for:

- Final Atlas Found and finding review
- Governance and structure mutation actions
- Inspect tabs
- Contextual Add

Slice 6C remains responsible for:

- Final staged Ask workflow
- Final packet, receipt, and handoff presentation
- Full app/API parity and mobile completion
- Native exact-source dogfood runbook and manual execution
- Release hardening and hosted validation checklist

Slice 6A alone does not make V1.7 code-complete or release-accepted. Manual
native-conversation proof, hosted Cloudflare D1 verification, production
project isolation, mobile and desktop hosted loops, and a real OpenAI handoff
or honest provider-blocked release state remain future acceptance gates.
