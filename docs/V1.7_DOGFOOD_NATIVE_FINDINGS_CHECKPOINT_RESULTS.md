# Campus Atlas V1.7 native findings and checkpoint-result blocker fix

## Status

This bounded release-blocker fix completes the missing native path from a
canonical checkpoint to a proposed Atlas Found finding. It does not govern the
finding, create retrieval authority, compile a packet, perform a handoff, or
begin the queued API-first architecture spike.

V1.7 remains **not release-accepted**. The dogfood run is paused before Cody's
first governance action.

## Confirmed root causes

1. The conversation workspace always submitted `findingCandidates: []`, so a
   native checkpoint could select nodes but could never create a finding.
2. Checkpoint health and the shared Reasoning Health service treated every
   `correction` event as an unresolved conflict, even when the correction and
   evidence were aligned.
3. The full checkpoint result lived only in client component state. Refresh
   showed the summary count but lost the selected nodes, omissions, missing
   state, ambiguity, findings, and retrieval-effect display.

## Canonical behavior

Native `canonical_case_events` checkpoints now own finding generation on the
server. The native request supplies only conversation, case, trigger, and
source mode. Client-supplied finding wording is rejected for this source.

The generator is deliberately sparse and deterministic:

- It considers only the checkpoint's selected canonical events.
- It proposes at most one atomic consequence from a bounded correction,
  mechanism candidate, principle candidate, or scope-changing constraint that
  already contains consequential language.
- It preserves the selected source statement instead of inventing a cleaner
  conclusion.
- It links the proposal to the originating checkpoint, selected reasoning
  nodes, and exact source events.
- It starts local, proposed, review-required, and non-governing.
- It creates no mechanism, governance event, or retrieval eligibility.
- It suppresses an unchanged equivalent proposal already present in the case.
- It returns zero findings when no selected source supports one safe atomic
  proposal.

The existing explicit-analyzer candidate contract remains available only for
the existing non-native analyzer/reconstruction sources. It does not restore
frontend authority to the native conversation path.

## Conflict semantics

A correction no longer creates Conflict merely because of its event type.
Conflict requires a canonical challenge, an explicit conflict/supersession
relationship in event metadata, or clear contradiction wording such as
`must not`, `no longer`, `contradicts`, or a prior proposition being wrong.

An aligned correction with a pending proposed finding therefore derives
`Awaiting governance`. Explicit contradictory corrections still derive
`Conflict`.

## Durable checkpoint inspection

`GET /api/v1/projects/:projectId/checkpoints/latest` reads the latest checkpoint
for the requested project, conversation, and case. It reuses the existing
checkpoint, selected-node, finding, and finding-version records; it creates
nothing.

The conversation workspace reads this endpoint after loading canonical
conversation state. A refresh restores:

- Checkpoint identity and status
- Candidate, selected, and omitted counts
- Selected node statements and representations
- Missing state and ambiguity
- Proposed findings
- Retrieval effect

The restored result is explicitly labeled as an existing canonical checkpoint
and remains readable without write authorization. The write key continues to
clear on refresh and is never persisted.
