# V1.7 Dogfood — Case-Aware Lineage Treatment

## Scope

This narrow release-blocker correction keeps the Slice 4 reconstruction pipeline intact while correcting two treatment errors found during the native Sports Engine dogfood run. It does not compile a packet, change governance, introduce authority, perform a handoff, or begin the queued API-first architecture spike.

## Confirmed root causes

1. The reconstruction interpreter verified the supplied case ID against the active project but discarded the canonical case objective before candidate discovery. Matching therefore relied only on the literal request, generic roadway mechanism text, and deterministic semantic families. A directly applicable `approved_local` mechanism could remain an indirect `Consider` item even when the task explicitly belonged to its exact case.
2. Candidate redundancy used normalized word-set equality. It could not recognize that a governing mechanism, its source finding, the checkpoint-selected supporting reasoning nodes, and their source events were stages of one canonical lineage rather than independent repetition.

## Case-aware matching

When a case ID is supplied, the server now:

- loads the case and objective through the project-scoped canonical case table;
- rejects a missing or cross-project case;
- ignores any client-supplied case-objective text;
- keeps the literal task unchanged;
- uses the canonical objective only when the literal task shares material bounded terms with it; and
- exposes whether canonical case context participated in matching.

Case membership does not force use. Existing task-mechanism, scope, authority, freshness, terminal-state, conflict, and project-isolation gates still run. Removing the active case, selecting another case, or submitting an unrelated task prevents the local mechanism from entering `Use`.

## Lineage-aware treatment

For a governing mechanism selected for `Use`, Atlas follows canonical relationships:

`Mechanism → source finding → supporting checkpoint nodes → source events`

Only nodes tied to the finding's source events, or explicitly recorded as supporting nodes, are represented by that mechanism. Represented ancestors remain present in the treatment result and later receipt/inspection lineage, but receive `Exclude` with:

> Represented by the approved governing mechanism; retained for lineage and audit, not counted as independent context.

Their independent-repetition contribution is zero and the governing mechanism records the represented ancestor IDs. Independent evidence, counterevidence, protected challenges, unresolved conflicts, required live state, and unrelated records are not collapsed.

The Stage 2 interface reports the number of lineage records retained so the default result can communicate one governed mechanism without hiding its provenance.

## Contract coverage

Automated coverage verifies:

- server-loaded canonical case objectives and ignored client injection;
- matching active-case use for an applicable approved-local mechanism;
- no use without the case, under another case, or for an unrelated task;
- project isolation;
- mechanism/finding/node/event lineage collapse;
- explicit lineage-only reasons and zero repetition contribution;
- protected counterevidence remains separate;
- preview produces no packet or canonical mutation; and
- existing Slice 4 conflict, unapproved-finding, authority, scope, immutability, and packet-receipt contracts remain green.
