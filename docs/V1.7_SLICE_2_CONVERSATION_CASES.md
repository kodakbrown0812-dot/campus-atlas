# Campus Atlas V1.7 Slice 2 conversation and case continuity

Slice 2 adds project-scoped canonical conversation ingestion and bounded case
continuity beside the V4.6 compatibility state. It does not add extraction,
findings, governance, mechanisms, roadways, packets, or model handoff.

## Canonical additions

- `conversation_imports` preserves the exact submitted source envelope,
  provenance, source format, content hash, diagnostics, and duplicate result.
- `messages.source_message_key` provides per-conversation idempotency without
  treating repeated message text as a duplicate.
- D1 triggers reject updates and deletes of canonical messages and import
  sources.
- `events.assignment_state` distinguishes assigned, unassigned, and chat-only
  events.
- `conversation_case_links` allows one conversation to retain multiple
  associated cases while `conversations.active_case_id` identifies current
  continuity. A partial unique index and service transaction enforce at most
  one active link per conversation.
- `case_boundary_proposals` separates a proposed boundary change from an
  applied change.
- `case_boundary_operations` and append-only attachment rows preserve apply and
  reversal history for attach, unassign, chat-only, move, split, and merge.
  Older operations cannot reverse across a newer unreversed operation affecting
  the same event.

Canonical IDs remain unchanged in D1 and API responses. Route segments and
fragment links encode those IDs, and the Worker decodes route segments before
validating and querying them.

## Domain API

All routes are project-scoped under `/api/v1/projects/:projectId`.

- `GET|POST /conversations`
- `POST /conversations/import`
- `GET /conversations/:conversationId`
- `GET /conversations/:conversationId/source`
- `POST /conversations/:conversationId/messages`
- `POST /conversations/:conversationId/active-case`
- `GET|POST /cases`
- `GET /cases/:caseId`
- `POST /events`
- `POST /case-boundaries/proposals`
- `POST /case-boundaries/proposals/:proposalId/apply`
- `POST /case-boundaries/operations/:operationId/reverse`

Writes retain the existing fail-closed bearer boundary. The minimum interface
lists project conversations, opens one preserved transcript, displays
provenance and exact import source, changes the active case only after canonical
confirmation, shows simple case state, and links events to their exact message.
The Slice 1 generic record API remains available for scoped reads, but rejects
direct writes to Slice 2-owned tables so callers cannot bypass import,
immutability, lineage, or boundary-history invariants.

## Import formats

- `text`: preserves the complete submitted text envelope. Recognized
  `User:`, `Assistant:`, `System:`, `Tool:`, `Cody:`, and `Amy:` markers produce
  ordered message records; unmarked text remains one exact message.
- `json`: accepts a message array, an object with `messages`, or a ChatGPT export
  object with `mapping`. Supplying JSON as a string preserves the exact source
  envelope; supplying an already-parsed value is explicitly diagnosed as a
  normalized envelope.

Imports require an idempotency key. Repeating either that key or the exact
source hash returns the existing conversation without adding messages.

The authentic raw Rockies–Brewers conversation has not been supplied. The

- Exact user/assistant message-sequence preservation

- Reconstruction generated independently from the raw conversation

These criteria are not simulated, waived, or reported as passing. The eventual
raw conversation and the present reconstruction must be linked as distinct
source layers: exact raw conversation and governed structured reconstruction.

lineage and independent-reconstruction behavior cannot yet be demonstrated.
