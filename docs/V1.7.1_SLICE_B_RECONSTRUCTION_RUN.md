## Scope

Slice B adds one operational endpoint:

`POST /api/v1/projects/:projectId/reconstruction/run`

The endpoint requires the existing canonical write authorization and an
`Idempotency-Key`. A new key reruns the current server-owned Need Gate,
interpretation, and candidate preview before it calls the existing canonical
packet compiler. An exact replay returns the saved immutable packet and
receipt before any current-state preflight. A successful first request creates
exactly one immutable packet, its packet items, and one receipt through the
existing atomic D1 batch.

Slice B does not add a provider call, receiving-model adapter, handoff,
answer, schema migration, roadway, ranking rule, treatment rule, UI change,
MCP adapter, embedding search, vector database, background maintenance, or
automatic governance.

## Request contract

Accepted JSON fields are exactly:

- `task`
- `requestedOutput`
- `caseId`
- `roadwayOverride`
- `tokenBudget`, limited to 400, 800, or 1,600

The exact literal task is retained in the saved packet record and returned by
the façade. The server loads project, case, roadway, authority, eligibility,
treatment, candidate, finding, and mechanism state. Client-authored canonical
fields are rejected.

The `roadwayOverride` affects only the current run. It does not update the
roadway registry.

## Canonical services reused

- `checkContinuity` owns the `none` / `light` / `full` Need Gate and invokes
  the existing `interpretTask` and `previewPacketCandidates` services for a
  full check.
- `interpretTask` remains the canonical roadway, scope, ambiguity, case, and
  required-state interpreter.
- `previewPacketCandidates` remains the canonical discovery, ranking,
  authority, scope, freshness, conflict, lineage-collapse, and treatment
  preview.
- `compilePacket` remains the only packet renderer and packet/packet-item/
  receipt writer.
- `getPacket` remains the canonical immutable saved-snapshot read.

Slice B does not copy or fork these rules. A temporary second read/preview is
accepted: the preflight proves safety, and the compiler independently reruns
its canonical logic immediately before writing.

## Mandatory no-write preflight for new runs

After pure request validation and a project-scoped idempotency lookup,
`reconstruction/run` performs a fresh `continuity/check` only when no saved
packet exists for that key. A previous client response is advisory and is
never accepted as authority for a new run.

Compilation stops with zero packet, item, receipt, handoff, answer,
governance, or provider effects when:

- Need is `none`
- Need is `light`
- Material ambiguity requires clarification
- Required current state is missing
- Minimum-safe content exceeds the selected budget
- The canonical roadway registry is unavailable
- The project or case is outside the requested scope
- Input contains unsupported client-authored canonical fields

The existing `/packets` compatibility route retains its prior behavior.
Slice B adds an optional compiler boundary used only by the façade so a race
that introduces missing state or an unsafe budget between preflight and final
rendering still stops before a failed packet is written.

## Canonical compilation and receipt

Only a current `full` and `ready` preflight reaches `compilePacket`.

The existing compiler continues to own:

- Interpretation and selected roadway
- Candidate discovery and deterministic ranking
- Authority, scope, freshness, conflict, and lineage boundaries
- Minimum-safe and final token limits
- Packet rendering
- Prior-comparable packet lookup
- Packet difference
- Governance causes
- Immutable packet items
- Immutable receipt
- Atomic D1 batch

The façade rereads the saved packet and receipt and returns a compact
projection of that exact snapshot. It does not render or recompile another
packet for presentation.

The projection contains:

- Packet ID, version/status, budget, final count, exact compiled content,
  prior comparable packet, and timestamp
- Roadway ID, version, and name
- Governing-mechanism, required-check, Consider, audit-only provenance,
  protected-correction, protected-conflict, and strongest-challenge summary
- Exact saved canonical receipt treatment snapshot and compact counts
- Governance causes, freshness, inference disclosure, unresolved conflicts,
  exact packet difference, and historical limitations
- Canonical packet, receipt, and Inspect links
- An honesty statement that supplied context does not establish outcome
  correctness
- Explicitly false handoff, provider-call, and authority-change effects

## Idempotency

The façade uses the existing project-scoped packet idempotency key.

An exact replay returns the original immutable packet and receipt with:

- `idempotentReplay: true`
- `packetCreated: false`
- `receiptCreated: false`
- `replaySource: saved_immutable_packet`
- `currentPreflightPerformed: false`
- Need reason code `idempotent_saved_reconstruction`

Pure syntax and unsupported-field validation still runs before replay lookup.
When a saved packet exists, Atlas loads only that packet and receipt, compares
the submitted request with the saved snapshot, and returns or conflicts
without invoking the current Need Gate, roadway interpretation, candidate
discovery, Exact-source expansion, or provider execution. Conflicting reuse
fails before any write. The comparison covers the exact task, requested
output, case ID, selected/overridden roadway consequence, and token budget
using saved packet and interpretation fields. The underlying compiler's
existing idempotency guard remains intact.

Replay does not claim that current canonical state was reevaluated or that the
same packet would be selected for a new request today. A caller that wants a
new current-state reconstruction must supply a new `Idempotency-Key`.

## Atomicity and immutability proof

Isolated-D1 tests prove:

- One successful run adds exactly one packet, its items, and one receipt.
- No conversation, message, event, case, checkpoint, node, finding,
  mechanism, governance event, handoff, or answer is created.
- An injected receipt-insert failure rolls back the packet and packet-item
  inserts in the same D1 transaction.
- Packet, packet-item, and receipt immutability triggers remain active.
- Reading the packet after creation returns the same snapshot and creates no
  new row.
- A deterministic blocked-preflight regression proves an exact replay still
  returns HTTP 200, the same packet/receipt/content, and zero row changes even
  when current roadmap, case, mechanism, and candidate reads would throw.

## Out-of-context retrieval trajectory (non-authoritative)

This section records research direction only. It does not change discovery,
ranking, treatment, packet compilation, or infrastructure in Slice B.

The desired larger-scale retrieval sequence is:

> semantic discovery + keyword precision + graph traversal → reranking →
> evidence grading → smallest useful subgraph

- Semantic search can find conceptually related material when vocabulary
  changes.
- Keyword search preserves exact names, identifiers, and phrases.
- Graph traversal follows relationships among people, concepts, cases,
  evidence, corrections, findings, and mechanisms.
- Reranking evaluates which discovered candidates actually answer the current
  task.
- Evidence grading distinguishes Exact transcript, observed fact, approved
  mechanism, summary, Reconstructed material, and inference.
- Packet compilation supplies only the smallest useful subgraph to a
  receiving model.

Atlas already has project/case scope, keyword/entity/relationship discovery
signals, canonical lineage, authority and representation grading,
deterministic treatment/reranking, and bounded packet compilation.

Large-scale true semantic or embedding-based retrieval has not been
technically validated. GPT-5.6 does not inherently inspect unlimited history
outside its active context window; a retrieval system must discover, grade,
and supply the relevant bounded packet.

Slice B adds no embedding model, vector database, external retrieval
provider, semantic index, new ranking method, or new source-expansion rule.
Those remain later research and trajectory-calibration work.
