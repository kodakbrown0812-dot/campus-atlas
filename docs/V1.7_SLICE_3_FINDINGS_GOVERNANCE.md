# Campus Atlas V1.7 Slice 3 checkpoints, findings, and governance

Slice 3 adds canonical checkpoints, sparse reasoning-node selection, atomic
findings, and backend-governed consequences beside the V4.6 compatibility
state. It does not add roadways, candidate ranking for task reconstruction,
packet compilation, receipts, model handoff, or the final navigation redesign.

The frozen authority remains
[`V1.7_IMPLEMENTATION_BLUEPRINT.md`](V1.7_IMPLEMENTATION_BLUEPRINT.md).

## Canonical additions

- `checkpoints` records the project, conversation, case, trigger, source,
  extraction version, start/end status, candidate/selected/omitted counts,
  Reasoning Health before/after, missing state, ambiguity, error, metadata, and
  project-scoped idempotency key.
- `checkpoint_reasoning_nodes` preserves which sparse nodes a checkpoint
  selected and their order.
- `finding_versions.proposal_hash` supports exact unchanged-proposal
  suppression after rejection. Existing rows receive an empty compatibility
  value; only Slice 3-created versions use a computed SHA-256 fingerprint.
- `findings.authority_state` is the canonical current-authority value returned
  consistently by governance mutations, refresh reads, and generic canonical
  reads.
- Governance events record prior/new status, the affected mechanism, and the
  event being rolled back. They also retain prior/new deferral return
  conditions and dates so rollback restores the complete prior state.
- Mechanisms retain the source finding that produced them.
- D1 triggers make reasoning-node versions, finding versions, mechanism
  versions, and governance events append-only.

`AtlasState` is not replaced. Slice 1 and Slice 2 canonical records retain their
existing ownership and behavior.

## Checkpoint behavior

All routes are project-scoped under `/api/v1/projects/:projectId`.

- `POST /checkpoints`
- `GET /checkpoints/:checkpointId`
- `GET /findings`
- `GET /findings/:findingId`
- `POST /findings/:findingId/governance`
- `POST /governance-events/:eventId/rollback`
- `GET /mechanisms/eligible`

Writes use the existing fail-closed bearer key and require an idempotency key.

A checkpoint considers only canonical events assigned or actively attached to
the requested conversation and case. Callers may narrow the candidate event
IDs, but cannot introduce an event from another case, conversation, or project.
Selection is deterministic and caps persisted checkpoint selections at seven.
Corrections, challenges, outcomes, decisions, and unknowns receive priority
before other case events. Every selected node cites its canonical source event.

The service does not invent event text or findings. An analyzer may submit
explicit atomic `findingCandidates`; omitting that array or supplying an empty
array is a valid successful checkpoint with “No durable finding proposed.”
Every proposed finding must cite one or more events considered by the
checkpoint. Candidate objects use a strict field set with one required
`proposalStatement`; additional consequence fields are rejected.

Supported checkpoint triggers are:

- `analyze_now`
- `conversation_pause`
- `case_switch`
- `decision_recorded`
- `outcome_recorded`
- `correction_recorded`
- `import_completed`

The extraction version is `slice3-sparse-v1`. Checkpoint creation is atomic:
the checkpoint, selected-node links and versions, and non-suppressed findings
commit together.

## Authority and governance

The initial finding version is an Atlas proposal and has no retrieval
authority. Supported actions are:

- Approve
- Revise
- Reject
- Defer
- Keep local
- Challenge

Approve and Keep local create a new Cody-reviewed finding version before any
authority changes. Revise creates a new `under_review` Cody version but no
retrieval eligibility. Defer requires a reason plus a return condition or date
and remains non-authoritative. Reject suppresses a byte-equivalent proposal
fingerprint from later checkpoints. Challenge excludes the proposal from
governing use.

An approved `mechanism_recognition` finding creates an immutable mechanism
version in the same D1 batch as the reviewed finding version, governance event,
and stable-record updates. `GET /mechanisms/eligible` reads only active
`approved_local` or `approved_project_wide` governing versions. A local
mechanism is filtered to its supporting case when `caseId` is supplied.

Rollback is itself a governance event. It requires the target event to remain
the latest governance action, appends a copy of the prior finding version, and
removes any resulting mechanism from eligibility through a new proposed
mechanism version. It never edits or deletes the original proposal, reviewed
version, approval, or mechanism version. Prior status, authority, scope,
deferral return condition, and expiration are restored from the immutable
governance event.

The Slice 1 generic governance-event write remains available for compatibility.
Appending that record alone cannot update a finding, governing version, or
eligible mechanism. Slice 3-owned stable/version records reject generic writes
so authority-bearing changes must use the domain transaction.

## Interface

The Slice 2 conversation workspace now exposes Analyze now for its active case.
It displays candidate, selected, and omitted counts, Reasoning Health
before/after, missing state, and the honest zero-finding result.

Project-scoped Atlas Found routes provide:

- A queue grouped into Needs review, Deferred, Conflict-related, and Recently
  resolved
- Finding review with the original Atlas proposal and every immutable version
- Exact event spans linked back to their canonical conversation messages
- Cody’s reviewed wording and an explicit local/project-wide scope
- All six Slice 3 governance actions
- Canonical governance history and retrieval effects

The interface waits for the backend response before showing an authority or
status change.

## Seeded fallback removal

`POST /api/structure` retains its V4.6 live structured-output contract when
`OPENAI_API_KEY` is available. When the key is absent or the model request
fails, it now returns an explicit `503` or `502` response with `proposal: null`
and `findingCreated: false`. It no longer substitutes the production
England–Ghana seeded proposal.

V4.6 England–Ghana fixture data remains available only to its existing
regression/demo surfaces. It is not presented as a canonical Slice 3
extraction result.

## Brewers proof and honest limitation

The byte-preserved Brewers source remains classified as
`user_supplied_case_reconstruction` with representation `Reconstructed`. Slice
3 proves that it can:

- Remain unchanged as the imported source artifact
- Produce an exact source event whose span resolves to that reconstructed
  artifact
- Produce a local, atomic mechanism-recognition proposal citing that event
- Preserve the node representation as `Reconstructed`
- Remain proposed with zero mechanisms and zero governance events until Cody
  acts

This is mechanism-proposal capability over a governed reconstruction, not proof
of historical raw-transcript ingestion. The unavailable original conversation,
original authorship/sequence, and original-message source spans remain the
explicit `deferred_historical_fixture_gap` documented in Slice 2. Slice 3 does
not relabel those tests or claim they passed.

## Acceptance coverage

The contract suite covers:

- At most seven selected nodes
- Zero findings as valid success
- Exact event lineage and refresh/API parity
- One finding/one consequence
- Cody revision governing while Atlas’s original remains
- Approval changing backend eligibility
- Rejection suppression
- Deferral remaining non-authoritative
- Project isolation
- Rollback without rewriting history
- Immutable version and governance records
- Brewers reconstructed-artifact mechanism proposal without automatic
  promotion
- Explicit model/key failure with no fabricated fallback

The five historical raw-Brewers tests remain visibly skipped. They are an
unavailable fixture gap, not a claimed pass.
