# Campus Atlas V1.7 — Authoritative Implementation Blueprint

**Status:** Frozen implementation authority  
**Starting point:** Campus Atlas V4.6 on `main` after the merged Slice 0 protection baseline and Slice 1 canonical-record foundation  
**Primary repository:** `kodakbrown0812-dot/campus-atlas`

This document supersedes earlier V4–V4.6 build directions wherever they conflict. Product improvements that are not required to resolve an inconsistency, implementation ambiguity, or acceptance-test failure must be deferred beyond V1.7.

# Part 1 — Product constitution, build boundary, and migration direction

## 1. Build objective

Modify the existing Campus Atlas application into a working **reasoning-context continuity steward**.

V1.7 succeeds when an authentic conversation produces a human-governed reasoning consequence, and that approved consequence legitimately changes the reconstruction packet provided to a later model for a differently worded but mechanically relevant task.

The production proof must show:

1. Cody conducts or imports an authentic conversation.
2. Atlas preserves the original transcript.
3. Atlas extracts only consequential events.
4. Atlas maintains or proposes a bounded case.
5. A checkpoint produces one atomic finding.
6. Cody reviews and may revise the finding.
7. Cody explicitly governs its final wording and scope.
8. Canonical retrieval eligibility changes.
9. A later task selects the correct reasoning roadway.
10. Atlas classifies candidates as Use, Consider, or Exclude.
11. The new packet differs from the baseline packet.
12. The receipt identifies the governance event responsible.
13. Amy receives the original task and Atlas packet as separate inputs.

V1.7 proves continuity, governance, reconstruction, and handoff. It does not need to prove that the final real-world answer is correct.

## 2. Product identity

Campus Atlas is a **governed reasoning-context continuity steward**.

It is not primarily:

- A memory dashboard
- A knowledge graph
- A general-purpose personal database
- A research chatbot
- A second Amy
- A model that decides what is true
- A replacement for the receiving model
- An autonomous learning system

Governing roles:

- **Amy or another receiving model reasons and answers.**
- **Atlas observes, preserves, organizes, and reconstructs consequential reasoning context.**
- **Rebar preserves continuity, lineage, authority, and reconstruction history.**
- **Cody governs consequential meaning.**
- **Live sources govern current external facts.**
- **The receipt explains what Atlas supplied and why.**

Core rule:

> Live sources govern current external state. Cody governs consequential meaning. Atlas reconciles and reconstructs both.

## 3. North-star behavior

Atlas should reduce the amount of reconstruction Cody must repeatedly perform without increasing the amount of structure Cody must manually manage.

The desired difference is:

> Looking up information about prior work versus reasoning from governed experience accumulated through prior work.

Atlas should make a receiving model feel as though it has responsibly kept up with the work—not because every prior conversation is dumped into the prompt, but because important consequences, corrections, mechanisms, conflicts, and current state are preserved and selectively reconstructed.

## 4. Constitutional rules

1. The current user request remains primary.
2. Amy reasons; Atlas reconstructs.
3. Atlas may propose structure but cannot silently create authority.
4. Cody’s explicit governance action is required for durable consequential meaning.
5. Live external facts and durable interpretations remain distinct.
6. Original source conversations remain intact.
7. Every consequential derived record retains source lineage.
8. Compression must not destroy reconstructability.
9. Exact, compressed, reconstructed, inferred, and conflicted representations remain distinguishable.
10. User corrections outrank model inference within their valid scope.
11. One finding contains exactly one proposed consequence.
12. Approval applies to Cody’s final reviewed wording and scope, not Atlas’s original wording.
13. Rejected proposals remain inspectable but cannot influence retrieval.
14. Unchanged rejected proposals cannot repeatedly resurface.
15. Mechanisms do not become universal because one case produced them.
16. Roadways encode reasoning structures, not predetermined answers.
17. Roadway selection occurs before context selection.
18. Mechanism and task fit outrank keyword or topic overlap.
19. Strong counterevidence travels with applicable mechanisms.
20. Unresolved conflict remains visible.
21. Historical packets are immutable.
22. Rollback creates a new governance event; it does not rewrite history.
23. Project isolation is enforced by the backend.
24. The UI and API read the same canonical authority state.
25. Failure is shown as failure.
26. Atlas does not imply ambient access to unsupported ChatGPT conversations.
27. Mobile and desktop expose the same functional governance loop.
28. Atlas prefers omission over exhaustive extraction.
29. Frequency and confidence may prioritize review but cannot create authority.
30. No frontend-only or seeded behavior may masquerade as the canonical V1.7 pipeline.

## 5. Adopted external architecture patterns

Atlas should reuse proven patterns for:

- Server-managed conversation state
- Immutable raw episodes
- Structured active context
- Archival retrieval
- Temporal validity
- Hybrid candidate discovery
- Thread-level versus long-term state separation
- Layered context assembly
- Human annotations and corrections
- Scoped memory
- Live validation
- Evaluation loops
- Auditability
- Future permission metadata

Adaptation rules:

- Memory blocks become project- and case-scoped records.
- Temporal facts retain source, scope, authority, and validity windows.
- Graph and hybrid retrieval propose candidates only.
- Long-term semantic memory becomes governed mechanisms and principles.
- Procedural memory becomes Blueprint rules and roadways.
- Model observations do not become authoritative merely because they were extracted.

Atlas differentiates through bounded cases, selective reasoning nodes, atomic findings, human-reviewed mechanisms, explicit authority transitions, intent-conditioned roadways, Use/Consider/Exclude treatment, counterevidence-preserving packets, packet diffs, and causal receipts.

> Atlas governs how authentic experience becomes legitimate future reasoning context.

> Project → Conversation → Message → Event → Case → Reasoning Node → Finding → Mechanism → Governed Principle → Roadway → Packet → Receipt

- Procedural: Blueprint rules, roadways, checks, failure modes, packet contracts

Every active case exposes a stable core:

- Objective
- Current decision or thesis
- Active constraints
- Most important correction
- Current Reasoning Health
- Required live state
- Next checkpoint or action

Initial Reasoning Health:

- Forming
- Missing information
- Awaiting decision
- Awaiting outcome
- Awaiting governance
- Conflict

Reasoning Health is derived, inspectable, and never a truth score or manually edited percentage.

# Part 2 — Canonical records, authority, persistence, and backend services

## 11. Canonical-state rule

The backend owns record identity, version, scope, authority, governing status, retrieval eligibility, lineage, packet history, and governance history.

The frontend may display drafts and loading states but cannot independently establish those properties.

## 12. Required canonical records

### Project

Fields: ID, name, description, owner actor, visibility, status, default token budget, schema version, legacy key, timestamps, metadata.

Invariant: another project’s records cannot influence retrieval without approved transfer.

### Conversation

Fields: ID, project, source type, title, provenance, import ID, active case, original time range, status, timestamps, metadata.

Invariant: native and imported conversations converge on one model; compression never replaces messages.

### Message

Fields: ID, conversation, sequence, actor type/ID, exact content, original timestamp, ingestion timestamp, source reference, content hash, metadata.

Invariant: exact content is immutable; duplicate imports are idempotent; derived events cite exact spans.

### Event

Types include objective, thesis, evidence, assumption, estimate, unknown, method, correction, challenge, decision, live-state change, outcome, postmortem, and constraint change.

Fields: ID, project, conversation, optional case, type, exact source span, compressed representation, source messages, actor, observed/ingested/validity times, extraction method/version, confidence, authority, version, metadata.

Invariant: not every message becomes an event; rejected interpretations do not erase sources.

### Case and case-event attachment

Case fields: ID, project, objective, thesis, decision, status, time horizon, scope, constraints, case core, outcome/postmortem state, timestamps, metadata.

Attachment fields preserve attachment state, actor, reason, start/end time, and supersession.

Invariant: consequential split, merge, move, or attachment changes preserve lineage and reversal.

### Reasoning node and version

Types: Fact, Assumption, Estimate, Unknown, Method, Correction, Challenge, Decision, Outcome, Constraint, Context, Mechanism candidate, Principle candidate.

Node fields: ID, case, type, current version, scope, authority, status, timestamps.

Version fields: statement, representation type, source events, evidence, counterevidence, uncertainty, confidence, creator, timestamp, superseded version.

Invariant: maximum seven selected nodes per checkpoint, normally three to five; edits create versions.

### Checkpoint

Fields: ID, case, conversation, trigger, source, start/end, status, extraction version, candidate/selected/omitted counts, health before/after, missing state, ambiguity, error.

Invariant: zero findings is valid; checkpoints cannot create authority.

### Finding and version

Finding types include case-boundary change, correction, mechanism recognition, scope revision, principle proposal, supersession, retirement, Blueprint revision, transfer, and compression confirmation.

Fields preserve project, case, checkpoint, sources, current version, status, return condition, expiration, and timestamps.

Version fields preserve proposal, scope, conditions, exclusions, evidence, counterevidence, uncertainty, surfacing reason, expected retrieval effect, creator, time, and supersession.

Invariant: one finding equals one consequence; unchanged rejected findings are suppressed.

### Mechanism and version

Mechanism retains stable ID, governing version, status, and timestamps.

Versions retain statement, scope conditions, exclusions, supporting cases/nodes, counterevidence, reality contact, authority, retrieval effect, creator, time, and supersession.

Invariant: versions are immutable; conflict and history remain preserved.

### Principle and Blueprint rule

Principles remain architecturally supported but need not dominate the first proof. Blueprint rules carry governed project methods, checks, counterarguments, live-state requirements, failure modes, and packet constraints.

Atlas may propose Blueprint changes but cannot silently edit approved content.

### Roadway and version

Fields: stable ID, project, name, current version, status, purpose, applicable/non-applicable intent patterns, checks, mechanism modules, live state, challenges, widening/narrowing rules, stop conditions, packet contract, authority, timestamps.

Invariant: one primary roadway per packet; roadways contain methods, not conclusions.

### Governance event

Actions: Approve, Revise, Reject, Defer, Keep local, Challenge, Supersede, Retire, Transfer, Roll back.

Fields: ID, project, actor, action, target type/ID, source/result version, prior/new authority, prior/new scope, reason, retrieval effect, timestamp, idempotency key.

Invariant: authority changes only through governance events.

### Live-state snapshot

Fields: ID, project/case, provider, source, entity, raw/normalized values, observed/validity/supersession times, freshness window, status, conflict group, metadata.

Invariant: live facts may update current state without human approval; durable interpretation still requires governance.

### Packet, packet item, receipt, and handoff

Packet fields: task, intent, primary roadway/version, supporting modules, token budget, compiled content, prior comparable packet, time, status, error.

Packet-item fields: source and version, Use/Consider/Exclude treatment, representation, scope, authority, freshness, reason, ordering.

Receipt fields: roadway reason, alternatives, candidate summary, governance causes, freshness, inference disclosure, conflict, diff, timestamp.

Handoff fields: packet, original task, model, time, live retrieval, final answer reference, status, failure.

Invariant: packets and receipts are immutable; original task and packet remain separate inputs.

## 13. Authority states

- Observed
- Inferred
- Proposed
- Under review
- Approved local
- Approved project-wide
- Approved cross-project
- Challenged
- Superseded
- Retired
- Rejected

Only scope-appropriate approved material may govern Use. Unapproved material may appear only as labeled local context, inference, Consider, challenge, or unresolved conflict.

## 14. Backend services

### Conversation service

Creates/imports conversations, appends and retrieves messages, detects duplicates, and preserves provenance.

### Event-extraction service

Detects candidate events, exact spans, compressed representations, and extraction versions. When analysis fails, preserve the source and create no fabricated finding.

### Case service

Owns active case, creation, boundary proposals, attachments, split/merge/move, reversal history, and case-core reconstruction.

### Checkpoint service

Runs defined triggers and Analyze now; produces candidates, selected nodes, omitted count, health, and zero or more atomic findings.

### Governance service

Transaction:

1. Validate actor and current version.
2. Validate scope.
3. Preserve Atlas proposal.
4. Create Cody-reviewed version if revised.
5. Create governance event.
6. Update governing version.
7. Recalculate eligibility.
8. Commit atomically.
9. Return exact downstream effect.

### Roadway service

Interprets intent, establishes project/case scope, selects one primary roadway, identifies supporting modules and required live state, exposes ambiguity, and accepts user correction.

### Candidate-discovery and ranking services

Discovery may use semantic similarity, BM25/keyword, entity, temporal, relationship, and scope signals.

Ranking evaluates:

1. Task/mechanism match
2. Scope fit
3. Authority
4. Evidence strength

Tie-break by reality contact, direct mechanism fit, applicable freshness, independent repetition, lower redundancy, and shorter equivalent representation.

### Packet compiler

Layer order:

1. Task and intent
2. Roadway and checks
3. Current state
4. Active case core
5. Cody corrections
6. Blueprint requirements
7. Approved mechanisms
8. Supporting cases
9. Strongest challenges
10. Unknowns/conflicts
11. Explicit exclusions
12. Authority/lineage

Token budgets: 400, 800 default, 1,600.

Compression removes redundancy first and never drops corrections, required checks, unresolved conflict, or strongest counterevidence merely to fit.

### Evaluation service

Permanent fixtures cover same topic/wrong mechanism, different wording/same mechanism, outcome-backed evidence versus speculation, user correction versus inference, local insight outside scope, conflict, stale state, rejection suppression, broad versus narrow requests, missing state, and token compression.

## 15. Transactions and idempotency

Use atomic transactions for governance, version changes, case split/merge, packet+receipt creation, transfer, and rollback.

Require idempotency for transcript imports, external writes, governance actions, packet compilation, handoffs, and provider-backed live ingestion.

# Part 3 — Frontend routes, product behavior, and canonical API integration

## 16. Frontend product rule and navigation

Primary progression:

> Continue conversation → inspect active case → analyze checkpoint → review one finding → govern one consequence → reconstruct later task → inspect packet change.

Primary destinations on desktop and mobile:

1. Work
2. Atlas Found
3. Ask
4. Inspect

Contextual Add is an action, not a fifth destination.

Remove Home/Projects dashboards, Review, Knowledge, Evidence, Graph, Workbench, Roadways, and Capture as peer top-level destinations.

Recommended routes:

- `/work`
- `/projects/:projectId/conversations/:conversationId`
- `/projects/:projectId/findings`
- `/projects/:projectId/findings/:findingId`
- `/projects/:projectId/ask`
- `/projects/:projectId/inspect`
- Project-scoped Inspect detail routes for cases, reasoning, mechanisms, and packets

Every project-scoped route enforces project ownership and resets stale client state on project switch.

## 17. App shell and Work

`AppShell` owns navigation, project switching, session identity, contextual Add, route loading, errors, and canonical-backend health. It does not own authority or eligibility.

The backend-health indicator distinguishes connected canonical state, loading, unavailable, explicit fixture mode, and failed persistence.

Work resumes meaningful activity. If an active conversation exists, Continue opens it directly. If none exists, offer Start conversation, Import conversation, and Add existing work.

Work cards show only title/objective, active case, Reasoning Health, meaningful change, pending findings, and next action.

## 18. Conversation workspace

The transcript is primary. Desktop uses transcript, sticky compact case bar, optional Atlas Found and Structure drawers, composer, and Analyze now. Mobile uses the same workflow with full-screen or bottom sheets.

Messages persist before the UI claims preservation. Imported/native messages share one display model. Source links scroll to exact spans.

The compact case bar shows project, active case, objective, status, primary Reasoning Health, freshness, latest checkpoint, and pending finding. Actions: Analyze now, Add, change case, view structure, open Atlas Found.

The Structure drawer exposes case core, events, nodes, evidence/challenges, mechanism candidates, outcome/postmortem, governance, and packet influence without requiring manual ontology management.

## 19. Analyze now

Visible stages:

1. Preparing source events
2. Identifying candidate structure
3. Selecting consequential nodes
4. Checking missing state and conflict
5. Creating findings
6. Complete
7. Failed or partial

Results show trigger, case, sources considered, candidate/selected/omitted counts, health before/after, missing state, ambiguity, findings, and current retrieval effect.

“No durable finding proposed” is a valid success.

## 20. Atlas Found and finding review

Atlas Found is an actionable governance queue, not a generic notification feed.

Sections: Needs review, Deferred, Awaiting outcome, Conflict-related, Recently resolved.

Each finding card shows what Atlas observed, one proposed consequence, why it matters, why uncertain, evidence, strongest challenge, scope, expected effect, and recommended action.

Finding review displays original proposal, Cody’s reviewed draft, exact diff, type, scope, conditions, exclusions, uncertainty, evidence, challenge, and expected retrieval effect.

Use explicit confirmation language such as:

> Approve this revised mechanism for Sports Engine project-wide retrieval.

The frontend waits for canonical governance confirmation before showing approval or removing the finding.

Deferral requires a reason and return condition/date and has no authoritative retrieval effect.

## 21. Ask with Atlas

Four stages:

1. Interpret
2. Treat candidates
3. Compile packet
4. Handoff and receipt

The roadway interpreter shows literal task, interpreted intent, primary roadway, modules, scope, live state, shared meanings, ambiguity, and alternatives. Material ambiguity pauses compilation.

Candidate treatment groups Use, Consider, and Exclude with source, type, scope, authority, freshness, reason, and strongest challenge.

Packet compiler offers 400, 800, and 1,600 tokens and fails explicitly when minimum safe context cannot fit.

Packet preview shows task, intent, roadway, current state, checks, mechanisms, evidence, challenges, corrections, unknowns/conflict, exclusions, authority/freshness, and lineage. Raw data remains available under Advanced and matches the same immutable snapshot.

Handoff visually separates:

- Your request
- Atlas reconstruction
- Model answer
- Receipt

## 22. Packet diff, receipt, and Inspect

Packet diff categories:

- Added
- Removed
- Representation changed
- Authority changed
- Scope changed
- Freshness changed
- Roadway treatment changed
- Use/Consider/Exclude changed

Every consequential row links to its cause.

Default receipt lineage:

1. Observed in
2. Atlas proposed
3. You decided
4. Atlas used it for
5. Packet changed

Inspect tabs:

- Cases
- Reasoning
- Mechanisms
- Principles
- Blueprint
- Packets

Advanced areas may expose governance, roadways, live snapshots, evaluations, and localized relationships. Default to vertical lineage, not a giant global graph.

## 23. Contextual Add, API, empty/error states, and mobile

Contextual Add types: Case, Research/evidence, Outcome, Correction, Challenge, Observation, Proposed connection.

Completion shows destination, created record, authority, source, suggested connections, next action, and whether retrieval changed.

Every consequential API mutation returns record/version, project, prior/new authority and scope, governing version, retrieval effect, governance event, timestamp, and idempotency result.

Optimistic UI may show loading and drafts but never approval, eligibility, permanent IDs, or packet-history changes before server confirmation.

Honest empty states replace seeded content. Visible errors cover conversation/import/checkpoint/canonical/governance/live-state/roadway/packet/handoff/parity failures and explain what remains valid.

The complete loop must work on mobile. Use bottom navigation, sticky case header, full-screen sheets, bottom sheets, collapsible packet sections, sticky governance actions, and touch-friendly source links.

## 32. Authentic proof sequence

1. Run and save a legitimate baseline later run-line task before approval.
2. Import authentic Brewers conversation with provenance and exact source.
3. Propose/correct case boundaries.
4. Run Analyze now or a defined checkpoint.
5. Produce selected nodes and one atomic finding when justified.
6. Let Cody revise, approve, keep local, defer, reject, or challenge.
7. Run the same or genuinely comparable later task.
8. Include the mechanism only when roadway, scope, authority, and evidence permit.
9. Show changed and unchanged packet items, governance cause, challenge, exclusions, and lineage.
10. Hand original request and packet separately to the receiving model.

The product must not force approval to make the demo succeed.

## 33. Permanent evaluation and parity

Track:

- Correct roadway and scope
- Approved mechanism inclusion
- Irrelevant exclusion
- Strongest-challenge retention
- Token count
- Human correction rate
- Packet-diff correctness
- Rejected-item suppression
- App/API agreement
- Honest compilation failure

For every governance action, compare app/API before and after, compile the next eligible packet, refresh, open a second session, and confirm ID/version/scope/authority/eligibility parity.
